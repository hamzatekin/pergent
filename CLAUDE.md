# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

pergent is a personal agent runner. Each task is a prompt plus a small JSON config; running a task spawns headless `claude -p` and stores the result, a structured "paper", on disk and in a SQLite index. The site, a TanStack Start app (React, server-rendered, Tailwind) installable as a PWA, renders the paper as the morning paper. Prompts and configs are edited in git only. No build step for the runner side (`src/`, `scripts/` run as they are); the only build is the site (`vite build`).

Keep it minimal: one feature per step, verified with a real run.

## Commands

Requires Node >= 24 (TypeScript runs directly via type stripping, so `.ts` files are executed with plain `node` and imports use `.ts` extensions).

```sh
npm run task -- list            # list tasks in tasks/
npm run task -- run <name>      # run one task, print output.md and a status line; exit 1 on failure
npm run task -- costs [name]    # last 20 runs per task from the database: status, turns, minutes, cost, and the average
npm run serve                   # the built site + API (+ /admin when ADMIN_PASSWORD is set) on http://localhost:4321 (serves dist/, so build first)
npm run dev                     # vite dev on http://localhost:4321: the same site with hot reload, no scheduler
npm run build                   # vite build: the TanStack Start app in app/ -> dist/client (browser) and dist/server (SSR)
npm run typecheck               # tsc for src/, then for app/
npm run lint                    # biome lint: the other check; `lint:fix` applies only its safe fixes
```

There are no tests. `npm run typecheck` and `npm run lint` are the checks. Biome (`biome.json`) is a linter only: the formatter and import sorting are off, so a lint run never rewrites a file, and `lint:fix` applies only its safe fixes. It leaves out `app/routeTree.gen.ts` (generated), `public/sw.js`, and `app/styles.css` (Tailwind's `@theme`/`@apply` is not CSS its parser reads). These rules are off on purpose: `noExplicitAny` (the task JSON is read as `any` at the edge and narrowed where used), `noArrayIndexKey` (the lists are rendered once on the server and never reordered or inserted into), `noDangerouslySetInnerHtml` (the site renders its own marked and cleaned newsletter HTML, under a CSP), `noNonNullAssertion` (92 places where the line above has just checked the value), `useTemplate`, `noAutofocus` (the login's only field, and the phrase just added to a never-show list), and `useLiteralKeys` (index signatures are read with brackets throughout, like the keys that cannot be dotted). The `task` and `serve` scripts (and the Dockerfile `CMD`) pass `--disable-warning=ExperimentalWarning` because `node:sqlite` still prints one on every start.

## Architecture

The runner layers are plain Node; the site is a TanStack Start app over them:

- `src/runner.ts` is the core. It loads a task from `tasks/<name>/`, creates `runs/<name>/<ISO timestamp>/`, optionally runs the task's `before` shell command in that directory, then spawns `claude -p --output-format stream-json --verbose --strict-mcp-config --setting-sources= --json-schema <PAPER_SCHEMA> --tools <allowedTools> --system-prompt <short>` with the run directory as cwd. On stdin go the task's `inputs` (files the `before` scripts wrote, each in a `<file name="…">` tag; tags rather than headings because the files have headings of their own), then `prompt.md`. It parses the stream for the final `result` event, whose `structured_output` is the paper, and writes `meta.json`, `output.json` (the paper), `output.md` (the paper rendered as markdown, so a run stays readable with `cat`), `log.jsonl`, `stderr.log`, and saves the run to the database at start, after a failed `before`, and at the end. Every child (the `before` shell and `claude`) is spawned detached as its own process group and stopped as a group, SIGTERM then SIGKILL 30s later: killing only the child let a process it started keep the output pipe open, and the run waited on it forever. `before` gets 5 minutes, `claude` the task's `timeoutMinutes`. Before commands run one at a time in the process (`oneAtATime`), since tasks fetch from the same places (FxTwitter answered 404 when news and tech fetched in the same minute; Reddit allows one RSS request a minute); the wait does not count toward the 5 minutes. When the runner itself gets SIGINT, SIGTERM or SIGHUP (a closed CLI terminal, a stopping container) it SIGKILLs the live groups before exiting. Each line of `log.jsonl` gets `t`, the seconds since `claude` started, which the dashboard shows per step. A result without a valid paper (the model answered in text, or the `StructuredOutput` tool call never came) is a failed run.
- `src/paper.ts` is the paper: the `Paper` type (`title`, `sections` with `heading`, optional `lead` markdown and `stories`; a story is `headline`, `body` markdown, optional `context` markdown, `source` URL and `importance` 1-3: 3 leads a section, 2 is a card, 1 is a brief; for the printed newspaper layout also `kicker` (üst başlık), `display` (the short printed headline), `spot` and `place`: `lead` for the manşet, `top` for the sürmanşet band above the masthead, `front` for the rest of page one, all only when the prompt asks), `PAPER_SCHEMA` (the JSON schema handed to claude, with the field descriptions the model sees), `parsePaper` (shape check on the structured output), `renderMarkdown` (markdown to HTML through `marked`, a link whose text is its URL becoming a "host ↗" chip), `canonical` (a URL without `utm_` parameters, hash or trailing slash, for matching images), `toMarkdown` (paper to the markdown the prompts used to ask for) and `fromMarkdown` (the reverse, for runs from before structured output: `# ` masthead, `## ` sections, `### ` stories, a blockquote opening with a bold label as the aside, a bare URL paragraph as the source). Every run, old or new, becomes a `Paper` before the site sees it, so there is exactly one rendering path for the cards (`app/server/paper-view.ts` and `app/components/Paper.tsx`) and one for the newspaper (`app/server/newspaper-view.ts` and `app/components/Newspaper.tsx`).
- `src/rate.ts` scores every story of a finished paper by how much it matters to the reader, with Jev, TypeSafe's System One model (`POST https://api.typesafe.ai/v1/systemone`, model `jev-latest`, typed questions in, calibrated answers out; docs at docs.typesafe.ai, index at `/llms.txt`). The runner calls it after parsing the paper, only when `TYPESAFE_API_KEY` is set and the task has a `reader` (news, tech and webdev; `"rate": false` turns it off anyway). One request per story, 8 at a time, retried twice on 429/529. The state is the task's `reader` (a few sentences on who reads the tab and what is high and low for them), the story as written, and `source_material`: the block of the run's input files that carries the story's source URL (matched with and without its query string), with the nearest `## ` group and `### @handle` headings above it. One Score question with four levels (not for them, loosely related, relevant, directly useful); Jev's score is the expected level, so it lands as `story.forYou`, 0-3 with two decimals, added to the paper before it is written (in `output.json` and the database; not in `PAPER_SCHEMA`, the model never sees it). Nothing shows it as a number: the page orders each section by it (`forReader` in `app/server/paper-view.ts`). A failed request leaves that story unscored and never fails the run; `rate.log` in the run directory has every score, error and the token count (about 800 input tokens a story). Until 2026-10-18 it rated sourcing, neutrality and substance into a 0-10 badge, which said nothing about whether to read a story and changed nothing on the page; old runs still carry that `rating` and the site ignores it.
- `src/images.ts` fills in lead images after the paper is written: for every story whose source is an article (not x.com, twitter.com or news.ycombinator.com) and has no image yet, it fetches the page's `<head>` (8s timeout, 512KB at most, 8 at a time, up to 80 stories) and takes its `og:image` or `twitter:image`, https only because of the page's CSP. Found images are merged into `images.json`, which the before scripts start with post photos and Bundle images; `images.log` has the count. Plain HTTP, no model, so it costs nothing in tokens; a failed page is skipped.
- `src/mute.ts` is the never-show list of a task with `"mute": true` (ideas; pains before it): phrases (a product, a source, or a headline standing for pains like it) kept in the database's `mutes` table, matched as whole words ignoring case (`mentions`, so "QuickBooks" matches `quickbooks-online`). The runner writes the list to `muted.md` in the run directory before `before` starts; `previous.ts` leaves matching stories out of `previous.md`, and a prompt that lists `muted.md` in `inputs` can tell the model to leave out what is still about one. The ideas radar sets aside posts that mention a phrase before its sort and its page hides problems that do; pains' list was copied to ideas once (`moveMutes` in `db.ts`). The server hides matching stories, in old papers too, checking the headline, body, aside, source URL and `sourceName` (the subreddit or forum), and says how many it hid. It imports nothing from `runner.ts` or `db.ts`, since the before scripts import it.
- `src/db.ts` is the index over runs: one `runs` table in `runs/pergent.db` (`node:sqlite`, built into Node, WAL mode; the file sits on the `runs` volume) holding the `RunMeta` fields plus `output` (markdown), the `images` map and `paper` (the structured output as JSON, null for runs from before it; added with a guarded `ALTER TABLE` on start), plus `state` (named values), `mutes` (the never-show lists, one phrase per row per task, unique ignoring case) `issues` (newsletter issues as published, one row per URL: what a run's `issues.json` held, saved by the runner right after `before`, whatever becomes of the paper) `posts` (the ideas radar's collected posts, one row per post, never deleted: what a run's `posts.json` held, saved the same way; a post Jev dropped keeps its row without its body, so it is not fetched and judged again), `problems` (a radar's problems: its `task` (ideas or gym, added with a guarded `ALTER TABLE`, the rows before it the ideas radar's), name, category, one-line summary, status open, starred, killed or merged, `judge_asked`), `verdicts` (every judgement of a problem: the verdict, hard no, scores, competitors, market, reason, test, and its mentions at the time), `overviews` (a radar's nightly overview, with its `task`: the summary, per category a one-line take, a summary and up to three ideas, and the hash of the board it was written from; the `briefs` table it replaced on 2026-11-12 stays in the database, unread), `mentions` (one row per sorted post: its problem, or none with a `note` saying why, and what the post says about it: recurring, cost, workaround, a quote) and `jobs` (the job market tracker's adverts, one row per advert, never deleted: what a run's `jobs.json` held, saved by the runner right after `before` with `first_seen`, and `last_seen` moved on each run that sees it again, so an advert no longer seen has closed; a known advert comes back without its body, which the row keeps from the first time; `jobs-read` adds what the model read from its text, `text_family`, `skills`, `nice_skills`, `min_years`, `text_sponsorship`, `ai_tools`, `fit`, `fit_why` and `read_at`, columns added with a guarded `ALTER TABLE` on start; adding `fit` cleared `read_at` once, so every advert was read again with it) and `homes` (the homes task's Rightmove rental listings, one row per listing, never deleted: what a run's `homes.json` held, saved the same way, with `first_seen` and `last_seen`, every rent it has had in `prices`, and `details`, the listing page's data as JSON, once fetched; the task's read adds `epc_band`, `epc_score`, `epc_from`, `fit`, `fit_why`, `read`, `read_at` and `read_pcm`, the rent it was read at, and the Homes page's Hide button `hidden_at`). The run directory stays the archive for the log, stderr, `before.log` and the fetched inputs, and is still what you open to debug. `openDb()` creates the table and backfills any run directory with a `meta.json` that has no row yet, so a fresh database (or a restored volume) catches up on start. Deleting a run directory does not delete its row. The `RunMeta` type is the contract; `toMeta`/`saveRun` map it to columns.
- `src/server.ts` is the production process (`npm run serve`, the image's `CMD`): a small Hono app on `@hono/node-server` that answers `GET /healthz`, serves `dist/client` (Vite's hashed `/assets/` cached for a year, plus `public/`'s icons, manifest and `sw.js`), hands every other request to the built site (`dist/server/server.js`, its `fetch`), closes stale runs (`closeStaleRuns`) and starts the scheduler. The site imports the runner side as `#src/...` (package.json `imports`), and `vite.config.ts` leaves those imports out of the bundle, so the built server loads `src/` as it is: one runner, one database connection and one set of live runs for the scheduler, the dashboard and the pages. Binds to 127.0.0.1 unless `HOST` says otherwise.
- `app/` is the site, TanStack Start v1 (`tanstackStart({ srcDirectory: "app" })`), file routes in `app/routes/` (`routeTree.gen.ts` is generated by the build and dev server, and committed). Every page is rendered on the server and hydrates; links between tabs and runs then navigate in the browser, preloaded on hover. Loaders call server functions (`app/server/*.functions.ts`, `createServerFn`, run on the server whether the page is rendered there or fetched by a navigation), and those return what the page shows, already formatted (dates in the task's `timezone`, markdown as HTML), so `marked` and the database never reach the browser and the page hydrates with the text it was rendered with. The reading routes are `/` and `/read/{-$task}/{-$runId}` (optional params: `/read`, `/read/<task>`, `/read/<task>/<runId>`); `getPaperPage` picks the run (the first task's latest ok one by default; an unknown task or run is `notFound()`, a 404), the older and newer runs, the notes (paused scheduler, failed run, no output, stories hidden), and `paperView` turns the paper into what `components/Paper.tsx` draws: each story's headline and body as one HTML string (a brief runs the headline into the first sentence), the aside as a closed `details` whose handle is the task's `contextLabel`, the source as a "host ↗" chip, the lead image looked up in the run's `images` by the story's canonical source URL, a section's cards in a `.stories` grid with a lead story two columns wide, then its briefs in one `.briefs` band headed by the task's `briefsLabel`; a run from before `importance` existed gets its first story per section as the lead. When the paper has for-you scores, the cards most worth the reader's time (`topPicks`: every card Jev scored 2 or more, at least 3 and at most 6, best first) come out of their sections into a first section, "Worth your time" ("Okumaya değer" in Turkish), the best as its lead and each card labelled with the section it came from; the rest stay in their sections, a section whose lead was picked gives the lead to its next card, and a section left empty is dropped. No score is ever shown. For a task with `"mute": true` it hides the muted stories (`src/mute.ts`), notes how many with a link to the list, and gives every story a "Never show" link to `/admin/mute/:task/:runId/:section/:story` (the story's place in the stored paper; `rel="nofollow"`, and a visitor without the admin cookie just meets the login). With the admin cookie and `ALETHEIA_CAPTURE_KEY` set, every story (cards and newspaper) also gets "Save to notes" (`components/SaveToNotes.tsx`): a form posting the story's place to `/admin/save`, which sends its headline, source, body and aside to Aletheia's capture API (`app/server/notes.ts`, `POST <ALETHEIA_URL>/api/capture`, default `https://aletheia.hamzatekin.dev`; a capture key can only add) under Inbox › today's date; the page's script posts it with `accept: application/json` and turns the button into a "Saved ↗" link to the new note, so the paper keeps its scroll, and without the script the server redirects back. A task with `newspaper` in task.json (news, tech and webdev) can also be shown as a printed daily after the Turkish papers Posta, Milliyet and Hürriyet, and its top bar gets a toggle between the cards ("Columns"), "Rows" (the same `paperView` drawn by `Paper` with `layout="rows"`: one story per row in a single 760px column, every story the same size, its image a thumbnail at the side, the briefs one list) and the newspaper (`components/LayoutToggle.tsx`, a form posting to `/layout` so it works before hydration; after it the click sets the cookie itself and reloads the data). The choice is kept per task in a `pergent_layout_<task>` cookie for a year (`app/layout.ts`); without one the task's `layout` decides (webdev sets `"cards"`), else the newspaper. News had a toggle once before, removed on 2026-10-17 and back on 2026-11-02. The newspaper: newsprint sheets, page one with the sürmanşet band above a red slab masthead (the config's `name` and `motto`, the date, the issue number counted from the task's ok runs, and the run's cost as the price), the manşet in Anton capitals, a section that is only its `lead` (tech's TL;DR list) as a box under it, a few stories in ruled columns and red boxes pointing inside (» 3'te), then a page per section with its header strip, the section's `lead` if it has one, a lead story, ruled columns and a Kısaca box. The words the page prints itself (Sayı/No., Fiyatı/Price, » 3'te/» Page 3, Kısaca/In brief) follow the task's `lang`, and a leading emoji is taken off headings and headlines (tech's prompt puts one on each). `getPaperPage` builds only the view the reader has chosen. With for-you scores, page one is the same `topPicks` the cards put at the top (the best as the manşet, the rest under it, the next three best in the sürmanşet band), whatever places the model chose; without them the model's `place` decides, and a paper from before the layout fields gets its page one from importance, one card per section in turn. Either way the inner pages are the rest, a page per section. The faces (Anton, Oswald, Source Serif 4, Alfa Slab One, with Latin Extended for Turkish) are Fontsource packages imported in `styles.css`, so Vite serves them from `/assets/` under the CSP. The page's `html lang` is the task's `lang`, its `<title>` the paper's title. Above every paper sits a closed Sources panel (`components/Sources.tsx`): one line naming what the task reads, and opened, how a run goes (schedule, the Jev filter, the memory, the model and its tools, the for-you score) and every source as a chip by kind (X handles by group, subreddits, newsletters…), built by `src/sources.ts` from the task's config and the scripts its `before` names, so it cannot drift from what is fetched; a new before script needs a case there to show up. Rendering a page does not count as a read for the scheduler; `PaperPage` sends `POST /api/read` once a run is open in the browser, and `Shell` once any page is open with the admin cookie (not on the reloads a page makes while a run is going), which is what counts (a crawler runs no script, so it cannot keep a forgotten deployment alive). The Newsletters page (`/newsletters/{-$feed}`, one issue at `/newsletters/<feed slug>/<id>`; `app/server/newsletters.functions.ts`, `components/Newsletters.tsx`) shows the issues of the `issues` table as published, without the model: a chip per newsletter (every `newsletters.feeds` name of any task, with its count), the issues newest first, an issue in one reading column with ←/→ to the same newsletter's older and newer issues and a link to the original. It is someone else's writing copied whole, so it is behind the admin cookie (a login without it, 404 without `ADMIN_PASSWORD`), and its sidebar link shows only with the cookie. The JSON API (`app/routes/api/`, server routes) stays for curl and debugging, read-only: `GET /api/tasks` (names), `GET /api/tasks/:name/runs[/:runId]` (only for a task in `tasks/`: the database still holds the runs of `today`, a private task built from the reader's notes and removed on 2026-10-19, and those stay unread) (a run is `meta`, `output`, `images` and `paper`; fetching one also counts as a read), `GET /api/status` (scheduler `off`/`on`/`paused`, last read, pause threshold), anything else under `/api` a JSON 404. Runs start from the scheduler, the dashboard or the CLI. `app/start.ts` is the request middleware: every response gets a CSP with a fresh nonce per request (`script-src` and `style-src` `'self'` plus the nonce, images from any https host), which `router.tsx` hands the router (`ssr.nonce`) so the hydration scripts it writes carry it; the model's markdown is set as HTML unsanitized, so the CSP is what keeps a script or an inline handler in it from running, and nothing may use an inline `style` attribute. It also keeps Start's CSRF check on server function calls.
- The dashboard under `/admin` is the same app (`app/routes/admin/`, `app/server/admin*.ts`), styled by the `.admin` rules in `app/styles.css`. The pages sit under the pathless `_authed` layout, whose `beforeLoad` asks `getAdminSession` and redirects to the login; every dashboard server function checks the cookie again in its own middleware, since a server function can be called directly. Every change is a plain HTML form posting to a server route (`/admin/login`, `/admin/logout`, `/admin/run/:task`, `/admin/mutes`, `/admin/mutes/remove`, `/admin/save`, `/admin/homes`), which answers with a redirect, so the forms work before the page hydrates. It exists only when `ADMIN_PASSWORD` is set (otherwise 404). Login is a form that sets an `HttpOnly`, `SameSite=Strict` cookie holding an HMAC of the password (30 days, path `/`, since the pages fetch their data from `/_serverFn/...`; changing the password logs everyone out; logging out also clears the old `/admin`-path cookie) and returns to the page that sent you there (`next`: a dashboard page, or the newsletters, ideas, jobs or homes, `app/next-path.ts`); a wrong password waits a second, and a POST whose `Origin` parses to another host is refused (our own forms send `Origin: null` because of `no-referrer`). `/admin` has a card per task (last run, average cost of the last 10, 30-day total, a Run now button that calls `startRun` in `src/scheduler.ts`, so it cannot overlap a scheduled run of the same task) and the latest 100 runs with status, turns, time and cost. `/admin/runs/:task/:runId` shows cost by model and tokens from the `result` event's `modelUsage`, `before.log`, `stderr.log` and the steps of `log.jsonl` (text, tool calls with their input, results, all cut short), and links every file in the run directory as plain text (`/files/:file`, only names that `readdir` returns). The never-show pages: `/admin/mute/:task/:runId/:section/:story` shows the story with one button per suggestion (its subreddit or forum, and "Pains like this one" for its headline) and a field for anything else, such as a product, `/admin/mutes/:task` is the list with an Undo per phrase, and both post to `/admin/mutes` (add, then back to the paper) and `/admin/mutes/remove`; a task card shows the count. Pages reload their data every 10s while a run is going (`router.invalidate()`). The server marks every row still `running` as `failed` when it starts (`closeStaleRuns`: a deploy or restart replaces the container, so nothing from before can still be going), leaving `finished_at` empty, which every other way a run ends sets, so the scheduler can tell a cut-off run from one that failed on its own. A row still `running` that is not the task's live run in this server (a CLI run) shows as `stopped`, and only the live run's time counts up. A manual run started after a task's slot counts for that slot, since the scheduler only looks at the runs started since the slot.
- `src/scheduler.ts` holds the runs this server has going (`startRun`, `isRunning`: one per task; at most `MAX_RUNS` (2) go at once, inside the container's 2 CPUs and 2 GB, and the rest wait in order, `isWaiting`, with the task card's button reading Waiting…) and runs tasks on their `schedule` cron string, only when `SCHEDULER=1` (the Dockerfile sets it; a local `npm run serve` never starts runs on its own, use the CLI). It ticks just after every minute boundary and matches five-field cron (`*`, lists, ranges, steps, Vixie-style dom/dow OR) against wall-clock time in the task's `timezone` (an IANA name; without one, the process `TZ`). A task is due when its cron fired in the last 24h and no run of it, whatever its status, has started since that slot (`runsSince`), so the same rule fires it on time and catches up a slot missed while the server was down, deploying or paused, without repeating a run. The exception is a run a restart cut off: a deploy stops the old container before starting the new one, so a deploy mid-run would lose the day's paper, and when the only run since the slot is one `closeStaleRuns` closed, the task runs once more. To trigger a run by hand, use Run now on `/admin`, or run the CLI inside the container: `docker exec -it pergent-app-1 node --disable-warning=ExperimentalWarning src/cli.ts run <task>`; the CLI does not see the server's in-flight runs, so not while a scheduled run is going. **Dead man's switch:** every run the UI fetches, and every page opened with the admin cookie (`components/Shell.tsx`, so following homes through Telegram and `/homes` counts), is recorded as `last_read` in the `state` table; after `SCHEDULER_PAUSE_DAYS` (default 7) without one the scheduler stops starting tasks, and the next read resumes it. A fresh database has no read, so a new deployment is quiet until the paper is opened once. This exists so a forgotten deployment cannot keep spending subscription usage; the server checks the pause state while rendering, before the page's script marks the read, so the page shows a note when runs were paused. With `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` set, the reader also gets a Telegram message a day before it pauses and one when it does (`pauseNotes`, once each per read, state `pause-warned` and `pause-paused`; marked sent before it goes, so a send that times out is not repeated every minute).
- What the browser gets besides the markup: `app/styles.css` (Tailwind v4 through `@tailwindcss/vite`, which finds the classes the components use on its own; the page's look is the component classes defined there with `@apply`), the components' small effects (`PaperPage`: ←/→ go to the older/newer run; `StoryImage`: feed thumbnails narrower than 300px and broken images are dropped, an image still loading is hidden (`data-loading`) and fades in once checked, one that loaded before hydration is checked at once, a portrait or square one is marked `tall` and shown whole (`object-contain` up to 26rem on the inset colour) instead of cropped to the 16:9 frame, which cut vertical video thumbnails in half; `Shell`: every page's frame, a sticky sidebar from `md` up (a link per task with its `icon`, the dashboard's Runs link when `ADMIN_PASSWORD` is set, the scheduler's state at the foot; `app/server/nav.ts` builds it) and on a phone the same links as a row in the top bar; `Topbar`: the sticky, translucent top bar with the page's title and actions, which on a phone slides away while scrolling down and comes back on any scroll up (`data-hidden`), set as an attribute so a scroll never re-renders; the root registers the service worker except on localhost) and `public/` (manifest, icons, `sw.js`; Vite copies them into `dist/client`). Light mode only, in the Linear and Vercel manner: a soft grey page (`--color-page`, not white, which was hard on the eyes) with white cards, a deeper grey sidebar, neutral greys, one indigo accent (`--color-accent`), one system sans (web fonts only in the newspaper layout), weight and grey for hierarchy rather than size. The motion and surface details (the strong `--ease-out` curve, the `shadow-border` ring on cards and chips instead of a border, `scale: 0.96` on press, the hairline on images) follow the two design skills in `.claude/skills/` (`emil-design-eng`, Emil Kowalski's, and `better-ui`, MIT, copied from skills.sh); read them before changing the UI. One reading column on a phone; from `md` the sidebar appears and the page widens and each section's cards (`.stories`) sit in a dense two-column grid, three at `xl`, a lead story spanning two; the section's briefs (`.briefs`) follow as one band whose lines flow in text columns. The PWA `start_url` is `/read`. `sw.js` is network-first for navigations with the last cached front page as the offline fallback, cache-first for `/assets/` and the icons, and leaves everything else (`/api`, `/admin`, `/_serverFn` data calls) to the network; bump its `CACHE` name when changing what it caches.

`src/cli.ts` is a thin wrapper over the same runner used by the server.

### Deployment

pier (`hamzatekin/pier`) deploys `compose.yaml` on the Hetzner box, checking `main` every minute (one `app` service, port 4321 exposed, `runs` and `claude-home` named volumes, capped at 2 CPUs, 2 GB and 512 processes) from the `Dockerfile` (multi-stage: `vite build` of the site, then a slim node 24 image with `@anthropic-ai/claude-code` installed globally, `npm ci --omit=dev` for hono, React, TanStack Start and marked, and `src/`, `scripts/`, `tasks/`, `dist/` copied; runs as root so the volumes are always writable). Traefik on the box does HTTPS; the domains and the www redirect are labels in `compose.yaml`. Variables, in `/srv/apps/pergent/.env` on the box: `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`; a container has no browser login). `TYPESAFE_API_KEY` turns on the for-you scores (and the Jev filter of news and the ideas radar). `TZ` is optional: compose defaults it to Europe/London, and it only sets the clock the prompts and `before` scripts see, not the schedule. `ADMIN_PASSWORD` turns on the dashboard. `ALETHEIA_CAPTURE_KEY` (optional) turns on Save to notes. `TRAVELTIME_APP_ID` and `TRAVELTIME_API_KEY` (optional) turn on the homes task's commute times, `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` (optional; the bot is @pergent_bot, the chat the reader's own with it) its messages, `EPC_TOKEN` (optional, from get-energy-performance-data.communities.gov.uk) its EPC register lookups and so the energy in its monthly total. A changed `.env` reaches the running container with `sudo -n pier pergent restart` on the box. The paper itself has no auth; it is open to anyone who reaches the domain. The server binds `HOST` (default loopback; the image sets `0.0.0.0`) and answers `GET /healthz` (in `src/server.ts`, before the site) for the compose `healthcheck` (Traefik only routes to healthy containers, and pier waits for healthy and goes back to the previous version otherwise; the check runs with `node -e fetch(...)` because the image has no curl). Tasks are baked into the image, so prompt changes deploy by push. README has the steps.

### Task layout

```
tasks/<name>/task.json   # config, see below
tasks/<name>/prompt.md   # sent verbatim on stdin to claude; a task without one is its before command alone
runs/<name>/<runId>/     # gitignored; one directory per run
```

`task.json` fields read by the runner: `model`, `allowedTools` (joined into both `--tools`, which limits the built-in tools the model has to exactly these, and `--allowedTools`, which pre-approves them; an empty list is `--tools ""`, no built-in tools at all), `inputs` (run-directory files joined into the prompt ahead of `prompt.md`), `systemPrompt` (replaces the runner's default one), `timeoutMinutes` (default 15, SIGTERM on expiry), `before` (shell command run in the run dir with `TASK_DIR` set to the task's directory), `contextLabel` (the aside's handle, also used when `output.md` is rendered), `reader` (who reads the tab and what is high and low for them: with `TYPESAFE_API_KEY` set, Jev scores every story against it, `src/rate.ts`, and the page orders each section by that score, a story under 1 dropping to the briefs, a brief from 2.5 becoming a card, the most relevant card the lead when the model gave the section one; the newspaper does the same per page, and a story moved to the briefs leaves page one; the best cards of the whole paper then go to the top, `topPicks`), `rate` (`false` turns off the for-you score even with a `reader`), `effort` (passed as `--effort`: how much the model reasons before answering, billed as output tokens; `news` sets `low`, since its runs spent over 4 minutes and about half of 43k output tokens after the last fetch on a paper of perhaps 20k), `mute` (`true` gives the task a never-show list, `src/mute.ts`: `muted.md` in the run directory, a "Never show" link on every story, muted stories hidden; add `muted.md` to `inputs` for the model to see it), `maxOutputTokens` (sets `CLAUDE_CODE_MAX_OUTPUT_TOKENS` for the run; the whole paper is one `StructuredOutput` reply, and one past claude's default 32k cap is cut off mid-JSON and arrives as `{}`, which fails the schema with "must have required property 'title'"). `schedule` is a five-field cron string read by the scheduler, in the task's `timezone` (IANA name, e.g. `Europe/London`; both tasks set it so the schedule does not depend on the container's `TZ`). Read by the server: `label` (the tab's text), `icon` (its sidebar icon, a name from `app/components/Icon.tsx`), `order` (where the tab sits, lower first, default 0, ties by name; the first task is the front page), `lang` (the page's `html lang`), `contextLabel`, `briefsLabel` (the briefs band's heading, "In brief" or "Kısaca"), `newspaper` (`{ name, motto }`: gives the task the printed newspaper layout beside the cards and names its masthead; the prompt should ask for `kicker`, `display` and `spot`, as news's, tech's and webdev's do, and `place`, which only matters for a paper without scores), `layout` (`"cards"`, `"rows"` or `"newspaper"`, the default, for a task with `newspaper`: the layout a reader who has not used the toggle gets), `tab` (`false` keeps a task that writes no paper out of the sidebar and the reading pages, which answer 404 for it; it still has its dashboard card and runs), `output` (a run that hands back something other than a paper, by name from `OUTPUTS` in `runner.ts`: the ideas radar's `sort`, `judge` and `overview`, the job tracker's `read`. Its `prepare` writes the input files after `before` and can end the run ok without claude when there is nothing to do, its schema replaces `PAPER_SCHEMA`, and its `save` stores the structured output and returns `output.md`; no rating, images or notify). Extra keys are allowed and are how `before` scripts get their own config (e.g. `tech` keeps its handle list under `"x"`).

Prompts describe the paper in terms of the schema's fields (`title`, sections with `heading`, `lead`, `stories`; stories with `headline`, `body`, `context`, `source`, `importance`) and end by asking for the structured output only. Both prompts tell the model to make a brief (importance 1) of anything worth a line but not a paragraph rather than drop it; `tech` is told the page replaces the newsletters, so it covers every item of every issue that way instead of picking a handful. The schema's field descriptions in `paper.ts` are part of what the model reads, so keep them and the prompts consistent.

### Why the claude invocation looks the way it does

- `ANTHROPIC_API_KEY` is deleted from the child env on purpose so `claude` falls back to the subscription login instead of billing an API key.
- The input files are in the prompt instead of being `Read` by the model: reading them cost a whole turn, their contents then rode along on every later turn, and `Read` cuts a file off silently at about 25k tokens. `tech` has no tools and writes the paper in its first turn; `news` has only `WebFetch`. `rate.ts` still finds its excerpts in the files on disk.
- `--system-prompt` replaces Claude Code's built-in system prompt, which is written for a coding agent and was sent on every turn. It and both prompts say in so many words to call `StructuredOutput` with the paper as its arguments, `sections` an array: told only to "return the structured output", haiku wrote the whole paper as a text reply, was made to call the tool and wrote it again, and sonnet once passed `sections` as a JSON string, was rejected and wrote it again. Either way the output tokens, the biggest cost of a run, doubled. It does not stop claude loading a `CLAUDE.md` above its cwd: a local run (run directories sit inside the repo) got this file and the user's own, about 33k tokens on every request, which pushed a homes read past Haiku's 100k price step. An empty `--setting-sources=` stops that, by loading no user, project or local settings (the Docker image has none of them; managed and remote settings still load). `--bare` would skip it too but only authenticates with `ANTHROPIC_API_KEY`, not the subscription token.
- `--strict-mcp-config` stops the headless run from inheriting the user's global MCP servers; a task only gets the tools its own config names.
- `--tools` alongside `--allowedTools`: `--allowedTools` alone only pre-approves, so a run could still reach Bash or Edit wherever settings allowed them (a test run of `news` did). `StructuredOutput` stays available, since `--json-schema` adds it (also with `--tools ""`), and a listed `WebFetch` is loaded directly instead of through ToolSearch.
- Model choice per task: use `claude-haiku-5-5` (Haiku 5.5, named by id rather than the `haiku` alias so the model does not change with the Claude Code version the image happens to install) when a `before` script has already fetched all the input and the job is summarizing (`tech`, the ideas radar's sort), `sonnet` when the task has to search the web or needs judgement over sources (`news` reads pre-fetched X posts but has to filter clickbait and propaganda and reconcile outlets, and its output is Turkish).

### `before` scripts

`tech` chains four: `previous.ts && fetch-x.ts && fetch-hn.ts && fetch-newsletters.ts` (each as `node ../../../scripts/<file>`). They run with the run directory as cwd, and a non-zero exit marks the run `failed` without starting claude; their output is in `before.log`.

- `scripts/previous.ts` (both tasks, first in the chain) writes `previous.md`: the headline and source of every story in the task's ok runs from the last `previous.days` (default 3), newest first, read from sibling run directories' `output.json` and capped at `previous.maxChars` (default 30000; older papers are dropped first). It is the memory: both prompts tell claude to leave out anything already in it and to run a story again only for a real new development, written about the new part. Runs from before structured output have no `output.json` and are not remembered.

- `scripts/fetch-x.ts` writes `tweets.md` (accounts from remote lists), `tweets-web.md` (hand-picked accounts) and `discourse.md` (techtwitter.com's public API, which needs a browser user agent). Posts come from FxTwitter's `/2/profile/{handle}/statuses`, no API key, 6 fetches in parallel, each page tried three times (3s, then 6s apart): FxTwitter pushes back with 404, not 429, and with both tasks fetching in the same minute big live accounts came back 404 and were missing. Handles come from two places under `task.json`'s `"x"` key: `lists` (JSON exports in the awesome-ai-x-accounts format, filtered by category id; an entry has a `file` relative to the task directory or a `url`) and `handles` (an object of group name to hand-picked handles). Output is grouped by category. With `images: true` (both tasks) each post's first photo or video thumbnail goes to `images.json` keyed by the post URL, from the same response, so a story sourced to a post gets its picture at no extra cost. The base AI list is the committed `tasks/tech/accounts.json`; the awesome-ai-x-accounts URL is still listed after it and only adds accounts when it answers, because that repo disappeared once (2026-09-20) and the 50 accounts in the file are what could be recovered from past runs' `tweets.md`. Every run also writes the merged list to `accounts.json` in the run directory, so the base list can be rebuilt from any run.
- `scripts/fetch-hn.ts` writes `hn.md`: the Hacker News front page plus stories over `hn.minPoints` in the last 24h, via the Algolia HN API.
- `scripts/fetch-newsletters.ts` writes `newsletters.md`: new issues from the feeds under `newsletters.feeds` (the four Cooperpress letters; The Deep View, Superpower Daily and MyClaw, daily AI letters on beehiiv and Ghost RSS; NativeWeekly, a beehiiv letter with RSS turned off, read from its sitemap with each post page's `#content-blocks` as the body), converted to text with links kept and with `display:none` elements (preview lines, tracking markers) dropped. `maxChars` is 90000 since the AI dailies add about 40k a day, and `tech` sets `maxOutputTokens: 64000` for the longer newsletter section. Every new issue, the deferred ones too, also goes to `issues.json` as cleaned HTML (plain tags only, a link's `href` and an image's https `src`, tracking links resolved, layout tables as divs), which the runner saves to the `issues` table for the Newsletters page. It also writes `newsletters.json` (the issue URLs delivered) and scans sibling run directories for earlier `newsletters.json` files, so an issue is delivered exactly once and missed days are caught up. The issue's own URL is taken out of the text (the bare line under the heading and every "Read on the Web" link to it), and `utm_` parameters are stripped from every link: with the issue URL there, the model sourced newsletter stories to the issue instead of the article. It and `previous.ts` are the only things that read earlier runs.

All six files (the five inputs and `previous.md`) are the task's `inputs`, joined into the prompt.

`news` (the Turkish daily paper; the task was called `haberler` until 2026-09-24, and `src/db.ts` moves its old run directories and rows to the new name on start) chains four: `previous.ts && fetch-x.ts && fetch-bundle.ts && filter-jev.ts`.

- `scripts/fetch-x.ts` again, configured under news's own `"x"` key with hand-picked handles only (no `lists`, `techtwitter: false`): the most followed Turkish news accounts on X (Pusholder, BPT, Boşuna Tıklama, which aggregate without reporters of their own, and the party-aligned Ajans Muhbir), international Turkish services, independent, left, opposition mainstream, journalists, fact-checkers, economy, sport, and government-aligned outlets (used for facts only, the prompt says so). It replaced the news-site RSS feeds. With `files: 4` and `out: "x"` the posts go to `x-1.md` … `x-4.md`, handles dealt round-robin so each file mixes the groups; `trim: "busiest"` makes the account with the most posts in a file lose its least-liked post first when the file goes over `maxChars`, so the high-volume aggregators cannot crowd out everyone else; `images: true` writes each post's first photo or video thumbnail to `images.json` keyed by the post URL, which is what stories use as `source`. Turkish text and URLs tokenize heavily, so files are kept at 38KB, not 60: at 45KB `Read` still cut off around line 130 and claude had to re-read with an offset. ZAM Haber is left out (suspended); an account that has gone is listed as `failed` in `before.log`. x.com links cannot be opened with `WebFetch`, so the prompt only fetches article links that appear in a post. It allows at most 5 fetches, all in one turn: runs used to take the whole 10 minutes, and every fetch as its own turn re-sends the ~70k tokens of Turkish input. It also says never to chase redirects or shortened links (bbc.in, trib.al), and caps the paper at 25 stories, 15 briefs and 6 "Ne olmuştu?" blocks: a longer Turkish paper went past 32k output tokens and was cut off. The task sets `maxOutputTokens: 64000` (Sonnet allows 128k) and `timeoutMinutes: 15` as headroom. The dashboard marks a paper step whose input arrived empty (cut off or unparseable); the real output tokens are in the cost-by-model table, since a stream event's usage is from the start of the message.
- `scripts/filter-jev.ts` removes clickbait, filler (horoscopes, guides, lists, ads) and praise or propaganda from the files under `filter.files`, in place, before the model reads them. Each item (a `- ` line and its indented lines) gets one Jev Choice question (`event`, `opinion`, `clickbait`, `filler`, `praise`), 20 items to a request, 6 requests at a time; an item goes only when its kind is a drop kind with probability at least `filter.threshold` (0.8), since Jev reads Turkish less well than English and reads literally (a critical report quoting a minister's "müjde" is a risk). Everything dropped is in `filter.log` with kind and probability; a failed request keeps its items; without `TYPESAFE_API_KEY` nothing is filtered. It is step one of moving `news` to haiku: filtering cuts what haiku would have to read (news sent about 150k tokens, and Haiku 5.5 charges five times as much for a prompt over 100k), and the switch waits until `filter.log` shows the judgement holds.
- `scripts/fetch-bundle.ts` writes `bundle.md`: the popular list and the last `bundle.hours` of the main feed from Bundle (bundle.app, the Turkish news aggregator app). Bundle has no official API; these are the keyless JSON routes its web client calls on `www.bundle.app/api/main` (`get-popular`, `get-feed` paginated with `beforeRssDataId`, and an unused `get-summary` POST that returns an AI summary with an importance flag), so they can change or block. The prompt uses the popular list as a second cross-source significance signal. It merges each item's `imageLink` into `images.json`.

`webdev` (`order: 1`, after tech, Sundays 09:00 London) is the weekly reading digest of the same eight newsletters tech reads, made after the reader's old ChatGPT task: about five Must read items (summary, why it matters, takeaway, whether to read it fully), then Web & mobile and AI & software engineering with a few stories and briefs each, ranked for a frontend-focused full-stack engineer who builds with React Native and Expo. Tech covers every item every morning; this is the five-minute pick of the week. It has `newspaper` and `layout: "cards"`, so it opens in cards with the toggle to the newspaper, and its prompt asks for `kicker`, `display` and `spot` but not `place` (its page one comes from the for-you picks). Its before is `previous.ts && fetch-newsletters.ts` under its own `newsletters` key (the same feeds, `days` 10, `maxChars` 300000, since a week of the three AI dailies is about 190k characters), and the delivered-once scan reads only `webdev`'s own run directories, so it gets every issue since its last run whatever tech has had. Sonnet with `WebFetch`: the prompt has it open the 6 to 8 strongest candidates in one turn and write those stories from the article, saying so when a page is paywalled or will not open. `previous.days` is 8, so last week's digest is the memory. The first run (27 issues, 8 fetches) took a minute and cost $0.72.

`ideas` (`tab: false`, every 3 hours London time, Haiku) is the ideas radar, which replaced the `pains` paper on 2026-10-20: it collects what UK and US small business owners post, sorts it into problems, and counts them, so the same complaint from five people is one problem with five mentions instead of five stories to read. The user's rules from pains stand: UK and US only, no dev tools, only what a couple of people with AI could build for (an add-on, an integration, an automation, a small app for one trade), not replacing QuickBooks, a bank or a marketplace, and not a big platform's own crashes, logins, support, fees or frozen accounts; sources stay free; code fetches and counts, the model only interprets. It is built in steps (the plan is `ideas/opportunity-radar-plan.md` in the project files): collect and sort, then a verdict per problem on whether it makes a business, then a nightly overview of the whole board. Since 2026-11-12 the verdicts and the overview judge for one person, a developer based in the UK who builds alone with AI (the reader's call); the sort prompts still say a small team, which only shapes what counts as a problem. The verdicts made before were left as they are (the reader's call) and are judged again the usual way, as a problem grows or its verdict turns 30 days old.
- Collect: `scripts/collect-posts.ts` reads the sources under `task.json`'s `"collect"` key: Reddit through Arctic Shift (`arctic-shift.photon-reddit.com/api/posts/search`, a free, keyless Reddit archive; every post of each subreddit in the last `hours`, paged 100 at a time oldest first; it answers 422 "Timeout. Maybe slow down a bit" or 429 when asked quickly, so requests go one at a time 2s apart with three retries, and a subreddit that still fails is caught up by the next run, whose 24h window overlaps), because Reddit stops serving RSS on 2026-11-13 and its logged-out JSON answers 403; Freelancer.com's open projects API per query, USD and GBP budgets only (a job paying someone to do a chore by hand is the plainest sign it is worth money); Square's seller community through Khoros's public LiQL API (`/api/2.0/search`), grouped by board. It skips every post already in the `posts` table (it opens `../../pergent.db` read-only), asks Jev the kind of each new one with `filter`'s kinds (`src/jev.ts`, shared with `filter-jev.ts`; `pain`, `chore-job` and `question` are kept, `build-job`, `promo` and `other` dropped at 0.6), and writes `posts.json`, which the runner saves to `posts`. A post is known by its Reddit id (`reddit:<id>`) or else its URL. While the table holds none of the radar's own posts it back-fills the posts of every pains run from their `pains.md` (what pains' Jev filter kept, no kind). A first run read about 500 posts, later ones about 100; `collect.log` has each source's count and Jev's tally by kind.
- Sort (`"output": "sort"`, `src/ideas.ts`): `prepareSort` writes `problems.md` (the categories, a fixed list in `CATEGORIES` or the task's `categories`, then every problem so far by category with its number) and `posts.md` (the newest kept posts no sort has seen, up to `sort.maxPosts` (250), bodies cut at `sort.bodyChars` (700), each under a ref p1, p2…; a backlog waits for the next runs, newest first), setting aside posts that mention a never-show phrase. Haiku (effort `low`: at the default it thought for 36k tokens and hit the output cap) says for every post which existing problem it raises, a new one, or none, plus `recurring`, `cost`, `workaround` and a short `quote`; `saveSortOutput` checks refs and numbers against `sort.json`, creates only the new problems some post went to, and stores a mention for every post of the batch (one left out of the answer gets a note, so it does not come back). The first real sort put 250 posts into 20 problems for $0.06; most posts raise none (one-off questions).
- Counts (`problemStats`, code): per problem, people (a source's author, or the post when the source names none), mentions, sources, paid jobs and budgets, how many say it recurs, name a cost or a workaround, first and last seen, and mentions per week for 8 weeks. The trend: New (first seen in the last 7 days, 2+ mentions), Rising (3+ this week and at least double its weekly average over the 4 weeks before), Steady (in 3 of the last 4 weeks), Fading (nothing in two weeks after 2+ in the four before).
- Verdict (`ideas-judge`, `tab: false`, 02:30 London, Sonnet with `WebSearch` and `WebFetch`, `"output": "judge"`, `src/ideas.ts`): `toJudge` picks up to `judge.maxProblems` (5) problems, asked ones first (`judge_asked`, set by the page's Judge again), then by people: open or starred, not muted, over the bar (`judgeBar`: 4 mentions from 3 people, or a paid job and 2 more posts), and never judged, grown by half since, or judged 30 days ago. `prepareJudge` writes `problems.md` with each problem's counts and up to 15 of its posts; nothing to judge ends the run ok without claude. The model checks the hard no's (not UK/US, a dev tool, only fixable by replacing a big platform or by its maker, needs a licence, not a software problem) and scores six questions 1 to 5 with a reason each (`QUESTIONS`: pain, willing to pay, gap, buildable, reachable, size), searching the web for the gap, plus competitors, a market guess, a reason paragraph and the smallest test. The scores are flat fields (`pain`, `pain_why`…): nested `{ score, why }` objects made Sonnet send bare numbers and write the answer again. Code derives the verdict (`verdictOf`): Pass for a hard no, buildable 2 or less, gap 1, or two answers of 2 or less; Worth testing for pain, pay and gap all 4 or more with buildable and reachable 3 or more; Watch otherwise. `verdicts` keeps every judgement. A run of 3 problems took a minute and cost $0.21. Buildable asks whether one person with AI could ship it in weeks and run it alone, Reachable whether a founder based in the UK can find and sell to these people.
- Overview (`ideas-overview`, 03:30 London, and `gym-overview`, 03:45, Sonnet without tools, `"output": "overview"`, `src/ideas.ts`): `prepareOverview` writes `board.md`, every problem raised by more than one person, or judged or starred, by category (the radar's `categories`, read from the radar's task.json, which is also the schema's enum), each with its counts, up to four costs named and workarounds, and its latest verdict with reason, smallest test and competitors; a category also says how many one-offs it leaves out. The model writes a summary of the whole board, and per category a one-line `take` for its card, a summary, and up to three `ideas` (name, pitch, why, risk, first step, the problems it answers, checked against `overview.json`, and `best` on at most three across the board); `overviews` keeps every one. The board's sha256 is stored with it, and a run whose `board.md` is the same as the last overview's ends without claude ("Nothing has changed since the last overview"). The first runs (2026-11-12, from the production data): ideas 134 problems, 54k input tokens, 40 seconds, $0.27; gym $0.06. It replaced the on-demand brief (`ideas-brief`, removed the same day).
- The Ideas page (`/ideas`, `/ideas?category=<slug>`, `/ideas/<id>`; `app/server/ideas.functions.ts`, `components/Ideas.tsx`) is behind the admin cookie like Newsletters (its sidebar link shows only with it), and goes from the overview down to the posts. The home: a chip per radar, the overview card (its summary, the ideas marked best as tiles linking to their category, when it was written, Refresh, a form posting to `/admin/ideas/overview` that starts the radar's overview run, and what became of the last run that wrote none: failed, or checked again with nothing new), a card per category with any problem (its take, problems raised by more than one person, people, how many are worth testing or to watch, how many ideas; a category with only one-offs says how many, so it can still be opened), the starred problems, then the Sources panel and how many posts are collected and sorted. The page refreshes itself every 5s while an overview is being written. A category: chips to the other categories, the overview's summary of it and its ideas (each with why, risk, first step and its problems as links), then its problems with chips by verdict (Worth testing, Watch, Not judged, Pass, Starred, Killed) and the one-offs behind a link, starred first, then by verdict, then most people, each with its verdict, its trend and an 8-week bar chart (an SVG with sizes as attributes, since the CSP allows no inline style). A problem's page (its category in the top bar links back to the category) has Star, Kill (hidden from the board except under Killed; its posts still land on it), Judge again (starts `ideas-judge` with the problem first) and Merge into another problem of its category (its mentions move; the old number redirects), all plain forms posting to `/admin/ideas/<id>`; then the verdict card (badge, earlier verdicts, hard no, reason, the six scores as dots with their reasons, the smallest test, what exists, the market guess), its counts, its weeks, and every post that raised it with its quote, cost, workaround and the full post. "Never show" links to the task's list at `/admin/mutes/ideas`.

`gym` (`tab: false`, every 6 hours at :40 London, Haiku at effort `low`, `"output": "sort"`, `"radarLabel": "Gym apps"`) is a second radar on the same tables and code: what people say about gym and fitness apps, sorted into problems a small team could build a better app for. Every radar query takes the radar's task (a post is the radar's that collected it, `posts.task`; a problem carries its `task`), so the two boards never mix, and a radar's judge and overview are the tasks named after it (`ideas-judge`, `ideas-overview`, `gym-overview`; `judgeOf`, `overviewOf` and `radarOf` in `src/ideas.ts`), the name being the only link between them; gym has an overview but no judge yet. Its sources, under its own `"collect"` in `scripts/collect-posts.ts`: App Store reviews (the public customer reviews feed, `itunes.apple.com/rss/customerreviews/page=N/id=<id>/sortby=mostrecent/json?cc=<country>`, 50 a page, about 500 newest per country; the country as `cc` rather than the `/gb/` path, which Apple's robots.txt asks bots to leave alone) and Google Play reviews (the `google-play-scraper` package, which reads what the Play website shows, one request per app with a 20s timeout: Play's country does not split its reviews, GB and US gave the same 150 for Hevy, so they are every country's in English) of `stores.apps`, rated `maxRating` (4) or less, the last `days` (7); Arctic Shift for the app subreddits (`subs`), the posts of big gym subreddits that name "app" (`search`: every post fetched and matched here, since Arctic Shift's full-text search over r/Fitness answered 422 "Timeout" more often than not) and their comments that do (`comments`, Arctic Shift's comment search); and YouTube comments under the most viewed recent videos of `youtube.queries`, only with `YOUTUBE_API_KEY` (YouTube Data API v3, free 10,000 units a day). Jev's kinds are its own (`complaint`, `wish` and `question` kept; `praise`, `promo` and `other` dropped), its categories (`categories`) and the sort's field descriptions (`sort.fields`) too. A store review's title starts with its stars ("2★"); a Play review or a comment has none of its own. An App Store feed with no review at all is named in `collect.log`, and every feed empty is flagged there as Apple refusing the address (it refused a home laptop on 2026-11-12 while the server's runs still got reviews). A shared EPC score, floor area or score-matched certificate is only a maybe, since flats alike in one block share those: both keep their rows, each with "Maybe also listed by", and both are messaged, the message saying "Maybe also listed by". Postcode, rent and size alone are nothing: on 2026-11-08 158 pairs matched on those, flats alike in one block.
- Score (`src/score.ts`, code only): each read listing gets a score out of 10, counted from task.json's `"score"` points (the reader chose code points over the model's 1 to 5 fit on 2026-11-08, to see why a listing scores what it does): space (2 beds or more 2, a 1-bed with a separate lounge 2, other 1-beds 1.5: the reader wants a 1-bed since 2026-11-10, a second bedroom fine but no better, a separate lounge a small plus), EPC by its number rather than its band (since 2026-11-14, the reader's call: an old terrace comes out a high D or a low C and is much the same either way): nothing up to `epc.zero` (55), `epc.points` (2) from `epc.full` (92), in a straight line between, so C 69 gets 0.8, C 80 1.4 and D 68 0.7; the number is the chart's, else the register certificate's when matched by address or the only one at the postcode, else the middle of the band ("EPC C (no number)"), each commute place's steps (Work up to 25 min 1.5, 32 min 1, 40 min 0.5; Centre up to 15 min 1, 25 min 0.5), crime (very low 1.5, low 1, average 0.5), heating (gas or a heat pump 1, communal or not said 0.5), and extras (0.5 for two, 1 for four or more of: a supermarket within `shops.metres`, a trip to the first commute place with no change, a quiet street, parking (the read's, or the agent's tick for a space of its own), a garden, furnished). A studio (no bedrooms, or no lounge) or a dealbreaking red flag (students, a room in a shared house, a short let) caps it at 1, very high crime at `veryHighCrime` (4); any other red flag, a deposit over the legal cap among them, takes `redFlag` (1) off; a read's flag about the crime, or about the deposit when code found it over the cap, is left out, since those are counted on their own. A dealbreaker is matched on the flag naming it ("students only", "room in a shared house", "short let", "studio"), so "near student halls" or "box room in the attic" is an ordinary flag. Nothing is stored: changing a weight re-scores every listing at once. The total is to one decimal, so the EPC number shows (it was to the nearest half until 2026-11-14, which rounded C 69 to C 78 alike). It orders the page, sets its Score 6+ chip, decides which matches get a message (`good`), and shows on each row and message with its parts. The first scores (157 read listings): 7 at most, the two 2-bed matches 6.5 and 6, the central 1-beds 4 (very high crime).
- Supermarkets (`src/shops.ts`, OpenStreetMap through the Overpass API, free, no key): every supermarket and convenience shop in the crime area, fetched before a read every `shops.days` (30) and kept in state `shops:<task>` (572 on 2026-11-08); a listing's nearest shop of `shops.brands` (Tesco, Lidl, Aldi, Sainsbury's, Asda, Morrisons, Co-op, Iceland, M&S, Waitrose, matched in the brand or name, so Tesco Express counts) as the crow flies, rounded to 50 m, goes into the model's text, the score's extras (within `shops.metres`, 800), the row's facts and the message. A failed fetch (an error, an answer with a remark, which Overpass sends with a 200 when a query runs out of time or memory, no shops, or under half the shops kept) keeps the old list.
- Messages (`notifyHomes` in `src/homes.ts`, `src/telegram.ts`, only with `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`): after each read is saved, every match worth a message (a score of `score.good`, 6, or more, whatever its bedrooms) and not hidden on the page that came up since messages were turned on (new to the table in the last `newDays`, 7, so a changed weight or a new shop that lifts a listing's score while it sits on the page sends nothing, and up on Rightmove at most three days before: a widened search brings old listings in as new), or got cheaper since, goes to the reader's Telegram chat once per rent (`notified_pcm`; again only when the rent drops, saying what it was): the photo, rent, EPC, score, commute, the note, the score's parts that earned points, bills, furnishing, availability, deposit and the agent, with buttons to the listing on Rightmove or OpenRent and to `/homes` (`notify.link`). At most `notify.maxMessages` (10) a run, the rest summed up in one line. A listing whose read is about to be redone (another rent, new commute times) or not yet timed to each place with a limit waits a run, since a message cannot be taken back. The first run with a bot only records when messages started (state `notify-since:<task>`) and says how many match now, so the listings already up never flood the chat. A failed send never fails the run; the rest go with the next read. Only a photo Telegram refuses (400) is sent again as text; a timeout is not, since the photo may have gone.

**Input sizes.** The per-file caps below come from when the model `Read` its inputs: `Read` returns at most about 25k tokens and cuts the rest off silently, which is why tweets are split into two files, post text is cut at 600 chars, the tweet files drop the least-liked posts past `x.maxChars`, and the newsletter file defers older issues past `newsletters.maxChars` to the next run. With the inputs now in the prompt that limit is gone and the caps (and the split into `x-1..4.md`, and `trim: "busiest"`) could become one size budget per task; they are unchanged so far. What still bounds them is cost per run: Haiku 5.5 has a 1M window but charges $0.10/$0.50 per million tokens only up to a 100k-token prompt and $0.50/$2.50 past it, so keeping a haiku task's prompt under 100k tokens cuts its cost by five. techtwitter.com is AI and startup heavy and has almost no web dev content, which is why HN and the web dev handle group exist.
