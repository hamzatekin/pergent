# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

pergent is a personal agent runner. Each task is a prompt plus a small JSON config; running a task spawns headless `claude -p` and stores the result, a structured "paper", on disk and in a SQLite index. The site, a TanStack Start app (React, server-rendered, Tailwind) installable as a PWA, renders the paper as the morning paper. Prompts and configs are edited in git only. No build step for the runner side (`src/`, `scripts/` run as they are); the only build is the site (`vite build`).

Keep it minimal: one feature per step, verified with a real run.

## Commands

Requires Node >= 24 (TypeScript runs directly via type stripping, so `.ts` files are executed with plain `node` and imports use `.ts` extensions).

```sh
npm run task -- list            # list tasks in tasks/
npm run task -- run <name>      # run one task, print output.md and a status line; exit 1 on failure
npm run task -- costs [name]    # last 20 runs per task from the database: status, turns, minutes, cost, and the average
npm run serve                   # the built site + API (+ /admin when ADMIN_PASSWORD is set) on http://localhost:4321 (serves dist/, so build first)
npm run dev                     # vite dev on http://localhost:4321: the same site with hot reload, no scheduler
npm run build                   # vite build: the TanStack Start app in app/ -> dist/client (browser) and dist/server (SSR)
npm run typecheck               # tsc for src/, then for app/
```

There are no tests and no linter. `npm run typecheck` is the only check. The `task` and `serve` scripts (and the Dockerfile `CMD`) pass `--disable-warning=ExperimentalWarning` because `node:sqlite` still prints one on every start.

## Architecture

The runner layers are plain Node; the site is a TanStack Start app over them:

- `src/runner.ts` is the core. It loads a task from `tasks/<name>/`, creates `runs/<name>/<ISO timestamp>/`, optionally runs the task's `before` shell command in that directory, then spawns `claude -p --output-format stream-json --verbose --strict-mcp-config --json-schema <PAPER_SCHEMA> --tools <allowedTools> --system-prompt <short>` with the run directory as cwd. On stdin go the task's `inputs` (files the `before` scripts wrote, each in a `<file name="…">` tag; tags rather than headings because the files have headings of their own), then `prompt.md`. It parses the stream for the final `result` event, whose `structured_output` is the paper, and writes `meta.json`, `output.json` (the paper), `output.md` (the paper rendered as markdown, so a run stays readable with `cat`), `log.jsonl`, `stderr.log`, and saves the run to the database at start, after a failed `before`, and at the end. Every child (the `before` shell and `claude`) is spawned detached as its own process group and stopped as a group, SIGTERM then SIGKILL 30s later: killing only the child let a process it started keep the output pipe open, and the run waited on it forever. `before` gets 5 minutes, `claude` the task's `timeoutMinutes`. Before commands run one at a time in the process (`oneAtATime`), since tasks fetch from the same places (FxTwitter answered 404 when news and tech fetched in the same minute; Reddit allows one RSS request a minute); the wait does not count toward the 5 minutes. When the runner itself gets SIGINT, SIGTERM or SIGHUP (a closed CLI terminal, a stopping container) it SIGKILLs the live groups before exiting. Each line of `log.jsonl` gets `t`, the seconds since `claude` started, which the dashboard shows per step. A result without a valid paper (the model answered in text, or the `StructuredOutput` tool call never came) is a failed run.
- `src/paper.ts` is the paper: the `Paper` type (`title`, `sections` with `heading`, optional `lead` markdown and `stories`; a story is `headline`, `body` markdown, optional `context` markdown, `source` URL and `importance` 1-3: 3 leads a section, 2 is a card, 1 is a brief; for the printed newspaper layout also `kicker` (üst başlık), `display` (the short printed headline), `spot` and `place`: `lead` for the manşet, `top` for the sürmanşet band above the masthead, `front` for the rest of page one, all only when the prompt asks), `PAPER_SCHEMA` (the JSON schema handed to claude, with the field descriptions the model sees), `parsePaper` (shape check on the structured output), `renderMarkdown` (markdown to HTML through `marked`, a link whose text is its URL becoming a "host ↗" chip), `canonical` (a URL without `utm_` parameters, hash or trailing slash, for matching images), `toMarkdown` (paper to the markdown the prompts used to ask for) and `fromMarkdown` (the reverse, for runs from before structured output: `# ` masthead, `## ` sections, `### ` stories, a blockquote opening with a bold label as the aside, a bare URL paragraph as the source). Every run, old or new, becomes a `Paper` before the site sees it, so there is exactly one rendering path for the cards (`app/server/paper-view.ts` and `app/components/Paper.tsx`) and one for the newspaper (`app/server/newspaper-view.ts` and `app/components/Newspaper.tsx`).
- `src/rate.ts` scores every story of a finished paper by how much it matters to the reader, with Jev, TypeSafe's System One model (`POST https://api.typesafe.ai/v1/systemone`, model `jev-latest`, typed questions in, calibrated answers out; docs at docs.typesafe.ai, index at `/llms.txt`). The runner calls it after parsing the paper, only when `TYPESAFE_API_KEY` is set and the task has a `reader` (news, tech and webdev; `"rate": false` turns it off anyway). One request per story, 8 at a time, retried twice on 429/529. The state is the task's `reader` (a few sentences on who reads the tab and what is high and low for them), the story as written, and `source_material`: the block of the run's input files that carries the story's source URL (matched with and without its query string), with the nearest `## ` group and `### @handle` headings above it. One Score question with four levels (not for them, loosely related, relevant, directly useful); Jev's score is the expected level, so it lands as `story.forYou`, 0-3 with two decimals, added to the paper before it is written (in `output.json` and the database; not in `PAPER_SCHEMA`, the model never sees it). Nothing shows it as a number: the page orders each section by it (`forReader` in `app/server/paper-view.ts`). A failed request leaves that story unscored and never fails the run; `rate.log` in the run directory has every score, error and the token count (about 800 input tokens a story). Until 2026-10-18 it rated sourcing, neutrality and substance into a 0-10 badge, which said nothing about whether to read a story and changed nothing on the page; old runs still carry that `rating` and the site ignores it.
- `src/images.ts` fills in lead images after the paper is written: for every story whose source is an article (not x.com, twitter.com or news.ycombinator.com) and has no image yet, it fetches the page's `<head>` (8s timeout, 512KB at most, 8 at a time, up to 80 stories) and takes its `og:image` or `twitter:image`, https only because of the page's CSP. Found images are merged into `images.json`, which the before scripts start with post photos and Bundle images; `images.log` has the count. Plain HTTP, no model, so it costs nothing in tokens; a failed page is skipped.
- `src/mute.ts` is the never-show list of a task with `"mute": true` (pains): phrases (a product, a source, or a headline standing for pains like it) kept in the database's `mutes` table, matched as whole words ignoring case (`mentions`, so "QuickBooks" matches `quickbooks-online`). The runner writes the list to `muted.md` in the run directory before `before` starts; `fetch-pains.ts` does not fetch a subreddit, query or forum whose name mentions a phrase and drops every post that mentions one, `previous.ts` leaves matching stories out of `previous.md`, and the prompt (which lists `muted.md` in `inputs`) tells the model to leave out what is still about one. The server hides matching stories, in old papers too, checking the headline, body, aside, source URL and `sourceName` (the subreddit or forum), and says how many it hid. It imports nothing from `runner.ts` or `db.ts`, since the before scripts import it.
- `src/db.ts` is the index over runs: one `runs` table in `runs/pergent.db` (`node:sqlite`, built into Node, WAL mode; the file sits on the `runs` volume) holding the `RunMeta` fields plus `output` (markdown), the `images` map and `paper` (the structured output as JSON, null for runs from before it; added with a guarded `ALTER TABLE` on start), plus `state` (named values), `mutes` (the never-show lists, one phrase per row per task, unique ignoring case) and `issues` (newsletter issues as published, one row per URL: what a run's `issues.json` held, saved by the runner right after `before`, whatever becomes of the paper). The run directory stays the archive for the log, stderr, `before.log` and the fetched inputs, and is still what you open to debug. `openDb()` creates the table and backfills any run directory with a `meta.json` that has no row yet, so a fresh database (or a restored volume) catches up on start. Deleting a run directory does not delete its row. The `RunMeta` type is the contract; `toMeta`/`saveRun` map it to columns.
- `src/server.ts` is the production process (`npm run serve`, the image's `CMD`): a small Hono app on `@hono/node-server` that answers `GET /healthz`, serves `dist/client` (Vite's hashed `/assets/` cached for a year, plus `public/`'s icons, manifest and `sw.js`), hands every other request to the built site (`dist/server/server.js`, its `fetch`), closes stale runs (`closeStaleRuns`) and starts the scheduler. The site imports the runner side as `#src/...` (package.json `imports`), and `vite.config.ts` leaves those imports out of the bundle, so the built server loads `src/` as it is: one runner, one database connection and one set of live runs for the scheduler, the dashboard and the pages. Binds to 127.0.0.1 unless `HOST` says otherwise.
- `app/` is the site, TanStack Start v1 (`tanstackStart({ srcDirectory: "app" })`), file routes in `app/routes/` (`routeTree.gen.ts` is generated by the build and dev server, and committed). Every page is rendered on the server and hydrates; links between tabs and runs then navigate in the browser, preloaded on hover. Loaders call server functions (`app/server/*.functions.ts`, `createServerFn`, run on the server whether the page is rendered there or fetched by a navigation), and those return what the page shows, already formatted (dates in the task's `timezone`, markdown as HTML), so `marked` and the database never reach the browser and the page hydrates with the text it was rendered with. The reading routes are `/` and `/read/{-$task}/{-$runId}` (optional params: `/read`, `/read/<task>`, `/read/<task>/<runId>`); `getPaperPage` picks the run (the first task's latest ok one by default; an unknown task or run is `notFound()`, a 404), the older and newer runs, the notes (paused scheduler, failed run, no output, stories hidden), and `paperView` turns the paper into what `components/Paper.tsx` draws: each story's headline and body as one HTML string (a brief runs the headline into the first sentence), the aside as a closed `details` whose handle is the task's `contextLabel`, the source as a "host ↗" chip, the lead image looked up in the run's `images` by the story's canonical source URL, a section's cards in a `.stories` grid with a lead story two columns wide, then its briefs in one `.briefs` band headed by the task's `briefsLabel`; a run from before `importance` existed gets its first story per section as the lead. For a task with `"mute": true` it hides the muted stories (`src/mute.ts`), notes how many with a link to the list, and gives every story a "Never show" link to `/admin/mute/:task/:runId/:section/:story` (the story's place in the stored paper; `rel="nofollow"`, and a visitor without the admin cookie just meets the login). With the admin cookie and `ALETHEIA_CAPTURE_KEY` set, every story (cards and newspaper) also gets "Save to notes" (`components/SaveToNotes.tsx`): a form posting the story's place to `/admin/save`, which sends its headline, source, body and aside to Aletheia's capture API (`app/server/notes.ts`, `POST <ALETHEIA_URL>/api/capture`, default `https://aletheia.hamzatekin.dev`; a capture key can only add) under Inbox › today's date; the page's script posts it with `accept: application/json` and turns the button into a "Saved ↗" link to the new note, so the paper keeps its scroll, and without the script the server redirects back. A task with `newspaper` in task.json (news) is shown instead as a printed Turkish daily after Posta, Milliyet and Hürriyet (the cards are only for the other tasks; news had a toggle between the two until 2026-10-17): newsprint sheets, page one with the sürmanşet band above a red slab masthead (the config's `name` and `motto`, the date, the issue number counted from the task's ok runs, and the run's cost as the price), the manşet in Anton capitals, a few stories in ruled columns and red boxes pointing inside (» 3'te), then a page per section with its header strip, a lead, ruled columns and a Kısaca box. `getPaperPage` builds only the newspaper view for such a task; a paper from before the layout fields gets its page one from importance, one card per section in turn. The faces (Anton, Oswald, Source Serif 4, Alfa Slab One, with Latin Extended for Turkish) are Fontsource packages imported in `styles.css`, so Vite serves them from `/assets/` under the CSP. The page's `html lang` is the task's `lang`, its `<title>` the paper's title. Above every paper sits a closed Sources panel (`components/Sources.tsx`): one line naming what the task reads, and opened, how a run goes (schedule, the Jev filter, the memory, the model and its tools, the for-you score) and every source as a chip by kind (X handles by group, subreddits, newsletters, GOV.UK pages…), built by `src/sources.ts` from the task's config and the scripts its `before` names, so it cannot drift from what is fetched; a new before script needs a case there to show up. Rendering a page does not count as a read for the scheduler; `PaperPage` sends `POST /api/read` once a run is open in the browser, which is what counts (a crawler runs no script, so it cannot keep a forgotten deployment alive). The Newsletters page (`/newsletters/{-$feed}`, one issue at `/newsletters/<feed slug>/<id>`; `app/server/newsletters.functions.ts`, `components/Newsletters.tsx`) shows the issues of the `issues` table as published, without the model: a chip per newsletter (every `newsletters.feeds` name of any task, with its count), the issues newest first, an issue in one reading column with ←/→ to the same newsletter's older and newer issues and a link to the original. It is someone else's writing copied whole, so it is behind the admin cookie (a login without it, 404 without `ADMIN_PASSWORD`), and its sidebar link shows only with the cookie. The JSON API (`app/routes/api/`, server routes) stays for curl and debugging, read-only: `GET /api/tasks` (names), `GET /api/tasks/:name/runs[/:runId]` (only for a task in `tasks/`: the database still holds the runs of `today`, a private task built from the reader's notes and removed on 2026-10-19, and those stay unread) (a run is `meta`, `output`, `images` and `paper`; fetching one also counts as a read), `GET /api/status` (scheduler `off`/`on`/`paused`, last read, pause threshold), anything else under `/api` a JSON 404. Runs start from the scheduler, the dashboard or the CLI. `app/start.ts` is the request middleware: every response gets a CSP with a fresh nonce per request (`script-src` and `style-src` `'self'` plus the nonce, images from any https host), which `router.tsx` hands the router (`ssr.nonce`) so the hydration scripts it writes carry it; the model's markdown is set as HTML unsanitized, so the CSP is what keeps a script or an inline handler in it from running, and nothing may use an inline `style` attribute. It also keeps Start's CSRF check on server function calls.
- The dashboard under `/admin` is the same app (`app/routes/admin/`, `app/server/admin*.ts`), styled by the `.admin` rules in `app/styles.css`. The pages sit under the pathless `_authed` layout, whose `beforeLoad` asks `getAdminSession` and redirects to the login; every dashboard server function checks the cookie again in its own middleware, since a server function can be called directly. Every change is a plain HTML form posting to a server route (`/admin/login`, `/admin/logout`, `/admin/run/:task`, `/admin/mutes`, `/admin/mutes/remove`, `/admin/save`), which answers with a redirect, so the forms work before the page hydrates. It exists only when `ADMIN_PASSWORD` is set (otherwise 404). Login is a form that sets an `HttpOnly`, `SameSite=Strict` cookie holding an HMAC of the password (30 days, path `/`, since the pages fetch their data from `/_serverFn/...`; changing the password logs everyone out; logging out also clears the old `/admin`-path cookie) and returns to the `/admin` page that sent you there (`next`); a wrong password waits a second, and a POST whose `Origin` parses to another host is refused (our own forms send `Origin: null` because of `no-referrer`). `/admin` has a card per task (last run, average cost of the last 10, 30-day total, a Run now button that calls `startRun` in `src/scheduler.ts`, so it cannot overlap a scheduled run of the same task) and the latest 100 runs with status, turns, time and cost. `/admin/runs/:task/:runId` shows cost by model and tokens from the `result` event's `modelUsage`, `before.log`, `stderr.log` and the steps of `log.jsonl` (text, tool calls with their input, results, all cut short), and links every file in the run directory as plain text (`/files/:file`, only names that `readdir` returns). The never-show pages: `/admin/mute/:task/:runId/:section/:story` shows the story with one button per suggestion (its subreddit or forum, and "Pains like this one" for its headline) and a field for anything else, such as a product, `/admin/mutes/:task` is the list with an Undo per phrase, and both post to `/admin/mutes` (add, then back to the paper) and `/admin/mutes/remove`; a task card shows the count. Pages reload their data every 10s while a run is going (`router.invalidate()`). The server marks every row still `running` as `failed` when it starts (`closeStaleRuns`: a deploy or restart replaces the container, so nothing from before can still be going), leaving `finished_at` empty, which every other way a run ends sets, so the scheduler can tell a cut-off run from one that failed on its own. A row still `running` that is not the task's live run in this server (a CLI run) shows as `stopped`, and only the live run's time counts up. A manual run started after a task's slot counts for that slot, since the scheduler only looks at the runs started since the slot.
- `src/scheduler.ts` holds the runs this server has going (`startRun`, `isRunning`: one per task; at most `MAX_RUNS` (2) go at once, inside the container's 2 CPUs and 2 GB, and the rest wait in order, `isWaiting`, with the task card's button reading Waiting…) and runs tasks on their `schedule` cron string, only when `SCHEDULER=1` (the Dockerfile sets it; a local `npm run serve` never starts runs on its own, use the CLI). It ticks just after every minute boundary and matches five-field cron (`*`, lists, ranges, steps, Vixie-style dom/dow OR) against wall-clock time in the task's `timezone` (an IANA name; without one, the process `TZ`). A task is due when its cron fired in the last 24h and no run of it, whatever its status, has started since that slot (`runsSince`), so the same rule fires it on time and catches up a slot missed while the server was down, deploying or paused, without repeating a run. The exception is a run a restart cut off: Coolify stops the old container before starting the new one, so a deploy mid-run would lose the day's paper, and when the only run since the slot is one `closeStaleRuns` closed, the task runs once more. To trigger a run by hand, use Run now on `/admin`, or run the CLI inside the container: `docker exec -it <container> node --disable-warning=ExperimentalWarning src/cli.ts run <task>` (Coolify's terminal button gets you there too); the CLI does not see the server's in-flight runs, so not while a scheduled run is going. **Dead man's switch:** every run the UI fetches is recorded as `last_read` in the `state` table; after `SCHEDULER_PAUSE_DAYS` (default 7) without one the scheduler stops starting tasks, and the next read resumes it. A fresh database has no read, so a new deployment is quiet until the paper is opened once. This exists so a forgotten deployment cannot keep spending subscription usage; the server checks the pause state while rendering, before the page's script marks the read, so the page shows a note when runs were paused.
- What the browser gets besides the markup: `app/styles.css` (Tailwind v4 through `@tailwindcss/vite`, which finds the classes the components use on its own; the page's look is the component classes defined there with `@apply`), the components' small effects (`PaperPage`: ←/→ go to the older/newer run; `StoryImage`: feed thumbnails narrower than 300px and broken images are dropped, an image still loading is hidden (`data-loading`) and fades in once checked, one that loaded before hydration is checked at once, a portrait or square one is marked `tall` and shown whole (`object-contain` up to 26rem on the inset colour) instead of cropped to the 16:9 frame, which cut vertical video thumbnails in half; `Shell`: every page's frame, a sticky sidebar from `md` up (a link per task with its `icon`, the dashboard's Runs link when `ADMIN_PASSWORD` is set, the scheduler's state at the foot; `app/server/nav.ts` builds it) and on a phone the same links as a row in the top bar; `Topbar`: the sticky, translucent top bar with the page's title and actions, which on a phone slides away while scrolling down and comes back on any scroll up (`data-hidden`), set as an attribute so a scroll never re-renders; the root registers the service worker except on localhost) and `public/` (manifest, icons, `sw.js`; Vite copies them into `dist/client`). Light mode only, in the Linear and Vercel manner: a soft grey page (`--color-page`, not white, which was hard on the eyes) with white cards, a deeper grey sidebar, neutral greys, one indigo accent (`--color-accent`), one system sans (web fonts only in the newspaper layout), weight and grey for hierarchy rather than size. The motion and surface details (the strong `--ease-out` curve, the `shadow-border` ring on cards and chips instead of a border, `scale: 0.96` on press, the hairline on images) follow the two design skills in `.claude/skills/` (`emil-design-eng`, Emil Kowalski's, and `better-ui`, MIT, copied from skills.sh); read them before changing the UI. One reading column on a phone; from `md` the sidebar appears and the page widens and each section's cards (`.stories`) sit in a dense two-column grid, three at `xl`, a lead story spanning two; the section's briefs (`.briefs`) follow as one band whose lines flow in text columns. The PWA `start_url` is `/read`. `sw.js` is network-first for navigations with the last cached front page as the offline fallback, cache-first for `/assets/` and the icons, and leaves everything else (`/api`, `/admin`, `/_serverFn` data calls) to the network; bump its `CACHE` name when changing what it caches.

`src/cli.ts` is a thin wrapper over the same runner used by the server.

### Deployment

Coolify deploys `compose.yaml` (one `app` service, port 4321 exposed, `runs` and `claude-home` named volumes, capped at 2 CPUs, 2 GB and 512 processes) from the `Dockerfile` (multi-stage: `vite build` of the site, then a slim node 24 image with `@anthropic-ai/claude-code` installed globally, `npm ci --omit=dev` for hono, React, TanStack Start and marked, and `src/`, `scripts/`, `tasks/`, `dist/` copied; runs as root so the volumes are always writable). Coolify's proxy does HTTPS. Variables, set in Coolify's UI: `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`; a container has no browser login). `TYPESAFE_API_KEY` turns on the for-you scores (and the Jev filter of news and pains). `TZ` is optional: compose defaults it to Europe/London, and it only sets the clock the prompts and `before` scripts see, not the schedule. `ADMIN_PASSWORD` turns on the dashboard. `ALETHEIA_CAPTURE_KEY` (optional) turns on Save to notes. The paper itself has no auth; it is open to anyone who reaches the domain. The server binds `HOST` (default loopback; the image sets `0.0.0.0`) and answers `GET /healthz` (in `src/server.ts`, before the site) for the compose `healthcheck` (Coolify ignores its UI health page for compose apps and Traefik only routes to healthy containers; the check runs with `node -e fetch(...)` because the image has no curl). Tasks are baked into the image, so prompt changes deploy by push. README has the steps.

### Task layout

```
tasks/<name>/task.json   # config, see below
tasks/<name>/prompt.md   # sent verbatim on stdin to claude
runs/<name>/<runId>/     # gitignored; one directory per run
```

`task.json` fields read by the runner: `model`, `allowedTools` (joined into both `--tools`, which limits the built-in tools the model has to exactly these, and `--allowedTools`, which pre-approves them; an empty list is `--tools ""`, no built-in tools at all), `inputs` (run-directory files joined into the prompt ahead of `prompt.md`), `systemPrompt` (replaces the runner's default one), `timeoutMinutes` (default 15, SIGTERM on expiry), `before` (shell command run in the run dir with `TASK_DIR` set to the task's directory), `contextLabel` (the aside's handle, also used when `output.md` is rendered), `reader` (who reads the tab and what is high and low for them: with `TYPESAFE_API_KEY` set, Jev scores every story against it, `src/rate.ts`, and the page orders each section by that score, a story under 1 dropping to the briefs, a brief from 2.5 becoming a card, the most relevant card the lead when the model gave the section one; the newspaper does the same per page, and a story moved to the briefs leaves page one), `rate` (`false` turns off the for-you score even with a `reader`), `effort` (passed as `--effort`: how much the model reasons before answering, billed as output tokens; `news` sets `low`, since its runs spent over 4 minutes and about half of 43k output tokens after the last fetch on a paper of perhaps 20k), `mute` (`true` gives the task a never-show list, `src/mute.ts`: `muted.md` in the run directory, a "Never show" link on every story, muted stories hidden; add `muted.md` to `inputs` for the model to see it), `notify` (`{ section, importance }`: after an ok run, `src/notify.ts` pushes the stories of at least that importance in sections whose heading contains `section` to the ntfy topic in `NTFY_TOPIC`, one message per run), `maxOutputTokens` (sets `CLAUDE_CODE_MAX_OUTPUT_TOKENS` for the run; the whole paper is one `StructuredOutput` reply, and one past claude's default 32k cap is cut off mid-JSON and arrives as `{}`, which fails the schema with "must have required property 'title'"). `schedule` is a five-field cron string read by the scheduler, in the task's `timezone` (IANA name, e.g. `Europe/London`; both tasks set it so the schedule does not depend on the container's `TZ`). Read by the server: `label` (the tab's text), `icon` (its sidebar icon, a name from `app/components/Icon.tsx`), `order` (where the tab sits, lower first, default 0, ties by name; the first task is the front page), `lang` (the page's `html lang`), `contextLabel`, `briefsLabel` (the briefs band's heading, "In brief" or "Kısaca"), `newspaper` (`{ name, motto }`: turns on the printed newspaper layout and names its masthead; the prompt must ask for `kicker`, `display`, `spot` and `place`, as news's does). Extra keys are allowed and are how `before` scripts get their own config (e.g. `tech` keeps its handle list under `"x"`).

Prompts describe the paper in terms of the schema's fields (`title`, sections with `heading`, `lead`, `stories`; stories with `headline`, `body`, `context`, `source`, `importance`) and end by asking for the structured output only. Both prompts tell the model to make a brief (importance 1) of anything worth a line but not a paragraph rather than drop it; `tech` is told the page replaces the newsletters, so it covers every item of every issue that way instead of picking a handful. The schema's field descriptions in `paper.ts` are part of what the model reads, so keep them and the prompts consistent.

### Why the claude invocation looks the way it does

- `ANTHROPIC_API_KEY` is deleted from the child env on purpose so `claude` falls back to the subscription login instead of billing an API key.
- The input files are in the prompt instead of being `Read` by the model: reading them cost a whole turn, their contents then rode along on every later turn, and `Read` cuts a file off silently at about 25k tokens. `tech` has no tools and writes the paper in its first turn; `news` has only `WebFetch`. `rate.ts` still finds its excerpts in the files on disk.
- `--system-prompt` replaces Claude Code's built-in system prompt, which is written for a coding agent and was sent on every turn. It and both prompts say in so many words to call `StructuredOutput` with the paper as its arguments, `sections` an array: told only to "return the structured output", haiku wrote the whole paper as a text reply, was made to call the tool and wrote it again, and sonnet once passed `sections` as a JSON string, was rejected and wrote it again. Either way the output tokens, the biggest cost of a run, doubled. It does not stop claude loading a `CLAUDE.md` above its cwd: a local run (run directories sit inside the repo) still gets this file; the Docker image has none. `--bare` would skip it but only authenticates with `ANTHROPIC_API_KEY`, not the subscription token.
- `--strict-mcp-config` stops the headless run from inheriting the user's global MCP servers; a task only gets the tools its own config names.
- `--tools` alongside `--allowedTools`: `--allowedTools` alone only pre-approves, so a run could still reach Bash or Edit wherever settings allowed them (a test run of `news` did). `StructuredOutput` stays available, since `--json-schema` adds it (also with `--tools ""`), and a listed `WebFetch` is loaded directly instead of through ToolSearch.
- Model choice per task: use `claude-haiku-5-5` (Haiku 5.5, named by id rather than the `haiku` alias so the model does not change with the Claude Code version the image happens to install) when a `before` script has already fetched all the input and the job is summarizing (`tech`, `pains`), `sonnet` when the task has to search the web or needs judgement over sources (`news` reads pre-fetched X posts but has to filter clickbait and propaganda and reconcile outlets, and its output is Turkish).

### `before` scripts

`tech` chains four: `previous.ts && fetch-x.ts && fetch-hn.ts && fetch-newsletters.ts` (each as `node ../../../scripts/<file>`). They run with the run directory as cwd, and a non-zero exit marks the run `failed` without starting claude; their output is in `before.log`.

- `scripts/previous.ts` (both tasks, first in the chain) writes `previous.md`: the headline and source of every story in the task's ok runs from the last `previous.days` (default 3), newest first, read from sibling run directories' `output.json` and capped at `previous.maxChars` (default 30000; older papers are dropped first). It is the memory: both prompts tell claude to leave out anything already in it and to run a story again only for a real new development, written about the new part. Runs from before structured output have no `output.json` and are not remembered.

- `scripts/fetch-x.ts` writes `tweets.md` (accounts from remote lists), `tweets-web.md` (hand-picked accounts) and `discourse.md` (techtwitter.com's public API, which needs a browser user agent). Posts come from FxTwitter's `/2/profile/{handle}/statuses`, no API key, 6 fetches in parallel, each page tried three times (3s, then 6s apart): FxTwitter pushes back with 404, not 429, and with both tasks fetching in the same minute big live accounts came back 404 and were missing. Handles come from two places under `task.json`'s `"x"` key: `lists` (JSON exports in the awesome-ai-x-accounts format, filtered by category id; an entry has a `file` relative to the task directory or a `url`) and `handles` (an object of group name to hand-picked handles). Output is grouped by category. With `images: true` (both tasks) each post's first photo or video thumbnail goes to `images.json` keyed by the post URL, from the same response, so a story sourced to a post gets its picture at no extra cost. The base AI list is the committed `tasks/tech/accounts.json`; the awesome-ai-x-accounts URL is still listed after it and only adds accounts when it answers, because that repo disappeared once (2026-09-20) and the 50 accounts in the file are what could be recovered from past runs' `tweets.md`. Every run also writes the merged list to `accounts.json` in the run directory, so the base list can be rebuilt from any run.
- `scripts/fetch-hn.ts` writes `hn.md`: the Hacker News front page plus stories over `hn.minPoints` in the last 24h, via the Algolia HN API.
- `scripts/fetch-newsletters.ts` writes `newsletters.md`: new issues from the feeds under `newsletters.feeds` (the four Cooperpress letters; The Deep View, Superpower Daily and MyClaw, daily AI letters on beehiiv and Ghost RSS; NativeWeekly, a beehiiv letter with RSS turned off, read from its sitemap with each post page's `#content-blocks` as the body), converted to text with links kept and with `display:none` elements (preview lines, tracking markers) dropped. `maxChars` is 90000 since the AI dailies add about 40k a day, and `tech` sets `maxOutputTokens: 64000` for the longer newsletter section. Every new issue, the deferred ones too, also goes to `issues.json` as cleaned HTML (plain tags only, a link's `href` and an image's https `src`, tracking links resolved, layout tables as divs), which the runner saves to the `issues` table for the Newsletters page. It also writes `newsletters.json` (the issue URLs delivered) and scans sibling run directories for earlier `newsletters.json` files, so an issue is delivered exactly once and missed days are caught up. The issue's own URL is taken out of the text (the bare line under the heading and every "Read on the Web" link to it), and `utm_` parameters are stripped from every link: with the issue URL there, the model sourced newsletter stories to the issue instead of the article. It and `previous.ts` are the only things that read earlier runs.

All six files (the five inputs and `previous.md`) are the task's `inputs`, joined into the prompt.

`news` (the Turkish daily paper; the task was called `haberler` until 2026-09-24, and `src/db.ts` moves its old run directories and rows to the new name on start) chains four: `previous.ts && fetch-x.ts && fetch-bundle.ts && filter-jev.ts`.

- `scripts/fetch-x.ts` again, configured under news's own `"x"` key with hand-picked handles only (no `lists`, `techtwitter: false`): the most followed Turkish news accounts on X (Pusholder, BPT, Boşuna Tıklama, which aggregate without reporters of their own, and the party-aligned Ajans Muhbir), international Turkish services, independent, left, opposition mainstream, journalists, fact-checkers, economy, sport, and government-aligned outlets (used for facts only, the prompt says so). It replaced the news-site RSS feeds. With `files: 4` and `out: "x"` the posts go to `x-1.md` … `x-4.md`, handles dealt round-robin so each file mixes the groups; `trim: "busiest"` makes the account with the most posts in a file lose its least-liked post first when the file goes over `maxChars`, so the high-volume aggregators cannot crowd out everyone else; `images: true` writes each post's first photo or video thumbnail to `images.json` keyed by the post URL, which is what stories use as `source`. Turkish text and URLs tokenize heavily, so files are kept at 38KB, not 60: at 45KB `Read` still cut off around line 130 and claude had to re-read with an offset. ZAM Haber is left out (suspended); an account that has gone is listed as `failed` in `before.log`. x.com links cannot be opened with `WebFetch`, so the prompt only fetches article links that appear in a post. It allows at most 5 fetches, all in one turn: runs used to take the whole 10 minutes, and every fetch as its own turn re-sends the ~70k tokens of Turkish input. It also says never to chase redirects or shortened links (bbc.in, trib.al), and caps the paper at 25 stories, 15 briefs and 6 "Ne olmuştu?" blocks: a longer Turkish paper went past 32k output tokens and was cut off. The task sets `maxOutputTokens: 64000` (Sonnet allows 128k) and `timeoutMinutes: 15` as headroom. The dashboard marks a paper step whose input arrived empty (cut off or unparseable); the real output tokens are in the cost-by-model table, since a stream event's usage is from the start of the message.
- `scripts/filter-jev.ts` removes clickbait, filler (horoscopes, guides, lists, ads) and praise or propaganda from the files under `filter.files`, in place, before the model reads them. Each item (a `- ` line and its indented lines) gets one Jev Choice question (`event`, `opinion`, `clickbait`, `filler`, `praise`), 20 items to a request, 6 requests at a time; an item goes only when its kind is a drop kind with probability at least `filter.threshold` (0.8), since Jev reads Turkish less well than English and reads literally (a critical report quoting a minister's "müjde" is a risk). Everything dropped is in `filter.log` with kind and probability; a failed request keeps its items; without `TYPESAFE_API_KEY` nothing is filtered. It is step one of moving `news` to haiku: filtering cuts what haiku would have to read (news sent about 150k tokens, and Haiku 5.5 charges five times as much for a prompt over 100k), and the switch waits until `filter.log` shows the judgement holds.
- `scripts/fetch-bundle.ts` writes `bundle.md`: the popular list and the last `bundle.hours` of the main feed from Bundle (bundle.app, the Turkish news aggregator app). Bundle has no official API; these are the keyless JSON routes its web client calls on `www.bundle.app/api/main` (`get-popular`, `get-feed` paginated with `beforeRssDataId`, and an unused `get-summary` POST that returns an AI summary with an importance flag), so they can change or block. The prompt uses the popular list as a second cross-source significance signal. It merges each item's `imageLink` into `images.json`.

`pains` (`order: 2`, after news and tech) collects what UK and US small business owners complain about, and what they pay others to do by hand, for finding a problem worth a paid product; dev tools are out of scope. It chains `previous.ts && fetch-pains.ts && filter-jev.ts`, and haiku writes the paper, one story per pain. `scripts/fetch-pains.ts` writes `pains.md` from keyless sources under `task.json`'s `"pains"` key, each item in a `## ` group (a subreddit, a board, a job query):
- `reddit`: a short list of multireddit requests (subreddits joined with `+`) through their RSS, which carries the whole post (the `.json` routes answer 403 since May 2026): a pain-phrase search over the last week ("is there a tool", "spreadsheet", "manually"…), then the newest 100 of the niche subreddits, then of the busy ones. Logged out, Reddit allows one RSS request a minute (`x-ratelimit-remaining` is 0 after one), so each request waits for `x-ratelimit-reset`; the first version fetched 14 subreddits 4s apart and from the server only the first one ever came back. A 403 stops the rest.
- `freelancer`: Freelancer.com's open projects API, per query, USD and GBP budgets only; a job paying someone to do a chore by hand is the plainest sign it is worth money.
- `khoros`: Square's seller community through Khoros's public LiQL API (`/api/2.0/search`), grouped by board; its product ideas board is sellers asking for what Square does not do.
`hours` (48) is the window for Reddit and Freelancer, `forumDays` (14) for Square's forum. At most `perGroup` (30) newest per group; bodies are cut shorter until the file fits `maxChars` (340000, about 85k tokens before the filter). No new fetch starts after `budgetSeconds` (180), so the script ends inside the before command's 5 minutes with what it has; each source's count or error is printed as it comes. `pains.json` lists the ids delivered and sibling runs' copies are skipped, so a post reaches the model once. Tried and left out: Hacker News (phrase searches found about ten comments in two days, none about running a business), UK Business Forums, Trustpilot and G2 (Cloudflare 429 or 403), WordPress plugin reviews (a few low ratings a month), and, removed on 2026-10-16 after none of the 116 stories of the week before came from them: 1 and 2 star App Store reviews of 17 business apps (Apple's customer reviews RSS; QuickBooks' iPhone app alone had 37 of 108 in two weeks, and its crash reviews made a story almost every day until the small-team rule), Shopify App Store reviews (parsed from HTML, about 4 in two weeks), the Shopify Community forum (Discourse `/c/<id>.json`) and MoneySavingExpert's small business boards (Vanilla `/api/v2/discussions`). Git has the code if one comes back. `filter-jev.ts` takes its kinds from `filter.kinds`, `filter.drop`, `filter.about` and `filter.threshold` (defaults are news's); `pains` keeps `pain`, `chore-job` and `question` and drops `build-job`, `promo` and `other` at 0.6, which cut 480 items to about 410 on a test run. `previous.days` is 14, and the prompt treats a pain that is in `previous.md` and comes up again as the strongest signal, the opposite of news. `rate` is off. The prompt keeps only pains a couple of people with AI could build for (an add-on, an integration, an automation, a small app for one trade), not replacing QuickBooks, a bank or a marketplace, and leaves out a big platform's own crashes, logins, support, fees and frozen accounts. `mute` is on, so a story's Never show link mutes its subreddit, forum, a product typed in, or its kind of pain (`src/mute.ts`). The plan past this step: a pain table in the database that outlives `previous.md`, and a weekly paper of ideas built from the pains raised by several people across sources.

`settlement` (`order: 3`, 07:00 London) watches the UK's "earned settlement" reform of indefinite leave to remain for the reader, a Skilled Worker in an RQF 3 job (SOC 3131) on today's 5-year route: the proposed 10 and 15-year periods, the earnings and conditions by RQF level, whether it applies to people already on a route, and the transitional rules and timing. One before script, `scripts/fetch-settlement.ts`, keyless, writes `settlement.md` from what is under `task.json`'s `"settlement"` key: the GOV.UK pages in `govuk.pages` through the content API (the consultation, the statements of changes collection, the Skilled Worker ILR guide and appendices, the white paper), listed every day with their last change and marked **CHANGED** with their change notes when this task has not reported that change; for a statement of changes a changed page cites (`HC 584`) or that is new in the collection, the Home Office written statement announcing it and, when new, its explanatory memorandum; Home Office, UKVI and MAC publications from GOV.UK's search API matching `govuk.match`; Home Office written statements and answers (questions-statements API, filtered by title in code since its `searchTerm` takes half a minute) and Hansard contributions; Google News RSS headlines (no article text); and the Free Movement, EIN and Commons Library feeds. `days` (3) is the window; `settlement.json` lists the ids delivered and sibling runs' copies are skipped, so each change reaches the model once. It also writes `last.md`, the newest ok paper in full, which is the memory: the paper always ends its fixed "Where things stand" section with the four questions, carried forward from `last.md` and changed only by new sources, and its "What changed" lead says plainly when nothing did. The prompt holds the position as of 2026-10-16 for a first run. Haiku, no tools, `rate` off; a run costs about $0.01. `notify` pushes a "What changed" story of importance 3 to the reader's phone through ntfy (`src/notify.ts`: the runner calls it after an ok run; `NTFY_TOPIC` is the secret topic, `NTFY_URL` another server, `PUBLIC_URL` makes it open the paper; `notify.log` in the run directory), so the prompt keeps 3 for an official decision on settlement or the Skilled Worker route and nothing else.

`webdev` (`order: 1`, after tech, Sundays 09:00 London) is the weekly reading digest of the same eight newsletters tech reads, made after the reader's old ChatGPT task: about five Must read items (summary, why it matters, takeaway, whether to read it fully), then Web & mobile and AI & software engineering with a few stories and briefs each, ranked for a frontend-focused full-stack engineer who builds with React Native and Expo. Tech covers every item every morning; this is the five-minute pick of the week. Its before is `previous.ts && fetch-newsletters.ts` under its own `newsletters` key (the same feeds, `days` 10, `maxChars` 300000, since a week of the three AI dailies is about 190k characters), and the delivered-once scan reads only `webdev`'s own run directories, so it gets every issue since its last run whatever tech has had. Sonnet with `WebFetch`: the prompt has it open the 6 to 8 strongest candidates in one turn and write those stories from the article, saying so when a page is paywalled or will not open. `previous.days` is 8, so last week's digest is the memory. The first run (27 issues, 8 fetches) took a minute and cost $0.72.

`today`, a private personal assistant page built from the reader's Aletheia notes, was removed on 2026-10-19 (it moves into Aletheia itself); git has its task, `fetch-aletheia.ts`, `briefings.ts` and the `private` flag if one comes back.

**Input sizes.** The per-file caps below come from when the model `Read` its inputs: `Read` returns at most about 25k tokens and cuts the rest off silently, which is why tweets are split into two files, post text is cut at 600 chars, the tweet files drop the least-liked posts past `x.maxChars`, and the newsletter file defers older issues past `newsletters.maxChars` to the next run. With the inputs now in the prompt that limit is gone and the caps (and the split into `x-1..4.md`, and `trim: "busiest"`) could become one size budget per task; they are unchanged so far. What still bounds them is cost per run: Haiku 5.5 has a 1M window but charges $0.10/$0.50 per million tokens only up to a 100k-token prompt and $0.50/$2.50 past it, so keeping a haiku task's prompt under 100k tokens cuts its cost by five. techtwitter.com is AI and startup heavy and has almost no web dev content, which is why HN and the web dev handle group exist.
