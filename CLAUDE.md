# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

pergent is a personal agent runner. Each task is a prompt plus a small JSON config; running a task spawns headless `claude -p` and stores the result, a structured "paper", on disk and in a SQLite index. The server renders the paper as a plain HTML page, installable as a PWA, that is the morning paper. Prompts and configs are edited in git only. No build step for the Node side; the only build is the stylesheet.

Keep it minimal: one feature per step, verified with a real run.

## Commands

Requires Node >= 24 (TypeScript runs directly via type stripping, so `.ts` files are executed with plain `node` and imports use `.ts` extensions).

```sh
npm run task -- list            # list tasks in tasks/
npm run task -- run <name>      # run one task, print output.md and a status line; exit 1 on failure
npm run task -- costs [name]    # last 20 runs per task from the database: status, turns, minutes, cost, and the average
npm run serve                   # site + API (+ /admin when ADMIN_PASSWORD is set) on http://localhost:4321 (serves dist/ for the stylesheet and static files, so build first)
npm run dev                     # the same with the server restarting on src/ changes and Tailwind rebuilding the stylesheet on save
npm run build                   # Tailwind CLI -> dist/styles.css, plus web/public/ and web/app.js copied into dist/
npm run typecheck               # tsc for src/ (web/app.js is plain JS)
```

There are no tests and no linter. `npm run typecheck` is the only check. The `task` and `serve` scripts (and the Dockerfile `CMD`) pass `--disable-warning=ExperimentalWarning` because `node:sqlite` still prints one on every start.

## Architecture

Seven layers, all small:

- `src/runner.ts` is the core. It loads a task from `tasks/<name>/`, creates `runs/<name>/<ISO timestamp>/`, optionally runs the task's `before` shell command in that directory, then spawns `claude -p --output-format stream-json --verbose --strict-mcp-config --json-schema <PAPER_SCHEMA>` with the prompt on stdin and the run directory as cwd. It parses the stream for the final `result` event, whose `structured_output` is the paper, and writes `meta.json`, `output.json` (the paper), `output.md` (the paper rendered as markdown, so a run stays readable with `cat`), `log.jsonl`, `stderr.log`, and saves the run to the database at start, after a failed `before`, and at the end. A result without a valid paper (the model answered in text, or the `StructuredOutput` tool call never came) is a failed run.
- `src/paper.ts` is the paper: the `Paper` type (`title`, `sections` with `heading`, optional `lead` markdown and `stories`; a story is `headline`, `body` markdown, optional `context` markdown, `source` URL and `importance` 1-3: 3 leads a section, 2 is a card, 1 is a brief), `PAPER_SCHEMA` (the JSON schema handed to claude, with the field descriptions the model sees), `parsePaper` (shape check on the structured output), `renderPaper` (paper to HTML, the one renderer: headline and headings escaped as text, bodies, leads and asides through `marked`, the source as a "host ↗" chip, the lead image looked up in the run's `images` by the story's source URL with tracking parameters stripped, the aside as a closed `details` whose handle is the task's `contextLabel`; a section's cards in a `.stories` grid with a lead story two columns wide, then its briefs in one `.briefs` band headed by the task's `briefsLabel`; a run from before `importance` existed gets its first story per section as the lead), `toMarkdown` (paper to the markdown the prompts used to ask for) and `fromMarkdown` (the reverse, for runs from before structured output: `# ` masthead, `## ` sections, `### ` stories, a blockquote opening with a bold label as the aside, a bare URL paragraph as the source). Every run, old or new, becomes a `Paper` before it is rendered, so there is exactly one HTML path.
- `src/db.ts` is the index over runs: one `runs` table in `runs/pergent.db` (`node:sqlite`, built into Node, WAL mode; the file sits on the `runs` volume) holding the `RunMeta` fields plus `output` (markdown), the `images` map and `paper` (the structured output as JSON, null for runs from before it; added with a guarded `ALTER TABLE` on start). The run directory stays the archive for the log, stderr, `before.log` and the fetched inputs, and is still what you open to debug. `openDb()` creates the table and backfills any run directory with a `meta.json` that has no row yet, so a fresh database (or a restored volume) catches up on start. Deleting a run directory does not delete its row. The `RunMeta` type is the contract; `toMeta`/`saveRun` map it to columns.
- `src/server.ts` is a Hono app on `@hono/node-server`. The reading routes (`/`, `/read`, `/read/:task[/:runId]`) are rendered whole on the server: the chrome (task tabs, older/newer links, the date stamp in the task's `timezone`, the paused-scheduler and failed-run notes) and the paper from `renderPaper`, with the paper's title as the `<title>`. A reader, a crawler and an LLM fetcher get the same page; there is no client-side rendering. `/` and `/read` show the first task's latest ok run; an unknown task or run is a 404. Rendering a page does not count as a read for the scheduler; `web/app.js` sends `POST /api/read` once a page with a run is open, which is what counts (a crawler runs no script, so it cannot keep a forgotten deployment alive). The JSON API stays for curl and debugging, read-only: `GET /api/tasks` (names), `GET /api/tasks/:name/runs[/:runId]` (a run is `meta`, `output`, `images` and `paper`; fetching one also counts as a read), `GET /api/status` (scheduler `off`/`on`/`paused`, last read, pause threshold). Runs start from the scheduler, the dashboard (`src/admin.ts`) or the CLI. Everything else is `serveStatic` over `dist/` (routing is non-strict, so a trailing slash is the same page). The stylesheet and `app.js` are linked with `?v=<mtime>` because the service worker caches by URL and the files are not hashed. Every response carries a CSP (`default-src 'self'`, images from any https host) because the page carries the model's markdown as HTML unsanitized. `onError` passes an `HTTPException` through with its own status instead of turning it into a 500. Binds to 127.0.0.1 only.
- `src/admin.ts` is the dashboard under `/admin`, server-rendered like the paper and styled by the `.admin` rules in `web/styles.css`. It exists only when `ADMIN_PASSWORD` is set (otherwise 404). Login is a form that sets an `HttpOnly`, `SameSite=Strict` cookie holding an HMAC of the password (30 days, path `/admin`; changing the password logs everyone out); a wrong password waits a second, and a POST whose `Origin` parses to another host is refused (our own forms send `Origin: null` because of `no-referrer`). `/admin` has a card per task (last run, average cost of the last 10, 30-day total, a Run now button that calls the server's `startRun`, so it cannot overlap a scheduled run of the same task) and the latest 100 runs with status, turns, time and cost. `/admin/runs/:task/:runId` shows cost by model and tokens from the `result` event's `modelUsage`, `before.log`, `stderr.log` and the steps of `log.jsonl` (text, tool calls with their input, results, all cut short), and links every file in the run directory as plain text (`/files/:file`, only names that `readdir` returns). Pages refresh every 10s while a run is going (a meta refresh, since the CSP allows no inline script). A row still `running` with no run going in this server shows as `stopped` (a restart cut it off). A manual run started after a task's slot counts for that slot, since the scheduler only looks at the latest run's start.
- `src/scheduler.ts` runs tasks on their `schedule` cron string, only when `SCHEDULER=1` (the Dockerfile sets it; a local `npm run serve` never starts runs on its own, use the CLI). It ticks just after every minute boundary and matches five-field cron (`*`, lists, ranges, steps, Vixie-style dom/dow OR) against wall-clock time in the task's `timezone` (an IANA name; without one, the process `TZ`). A task is due when its cron fired in the last 24h and its latest run, whatever its status, started before that slot, so the same rule fires it on time and catches up a slot missed while the server was down, deploying or paused, without ever repeating a run. To trigger a run by hand, use Run now on `/admin`, or run the CLI inside the container: `docker exec -it <container> node --disable-warning=ExperimentalWarning src/cli.ts run <task>` (Coolify's terminal button gets you there too); the CLI does not see the server's in-flight runs, so not while a scheduled run is going. **Dead man's switch:** every run the UI fetches is recorded as `last_read` in the `state` table; after `SCHEDULER_PAUSE_DAYS` (default 7) without one the scheduler stops starting tasks, and the next read resumes it. A fresh database has no read, so a new deployment is quiet until the paper is opened once. This exists so a forgotten deployment cannot keep spending subscription usage; the server checks the pause state while rendering, before `app.js` marks the read, so the page shows a note when runs were paused.
- `web/` is what the browser gets besides the page: `styles.css` (Tailwind v4, built by the Tailwind CLI into `dist/styles.css`; it scans `src/` for the classes `paper.ts` and `server.ts` emit), `app.js` (plain script, no build: ←/→ follow the older/newer links, feed thumbnails narrower than 300px and broken images are removed on load, `POST /api/read` marks the read, and the service worker is registered except on localhost) and `public/` (manifest, icons, `sw.js`; all copied into `dist/`). No framework, no client-side routing, no web fonts; light paper palette only, system serif. One reading column on a phone; from `md` the page widens and each section's cards (`.stories`) sit in a dense two-column grid, three at `xl`, a lead story spanning two; the section's briefs (`.briefs`) follow as one band whose lines flow in text columns. The PWA `start_url` is `/read`. `sw.js` is network-first for navigations with the last cached front page as the offline fallback, and cache-first for the static files; bump its `CACHE` name when changing what it precaches.

`src/cli.ts` is a thin wrapper over the same runner used by the server.

### Deployment

Coolify deploys `compose.yaml` (one `app` service, port 4321 exposed, `runs` and `claude-home` named volumes) from the `Dockerfile` (multi-stage: the Tailwind build, then a slim node 24 image with `@anthropic-ai/claude-code` installed globally, `npm ci --omit=dev` for hono and marked, and `src/`, `scripts/`, `tasks/`, `dist/` copied; runs as root so the volumes are always writable). Coolify's proxy does HTTPS. Variables, set in Coolify's UI: `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`; a container has no browser login). `TZ` is optional: compose defaults it to Europe/London, and it only sets the clock the prompts and `before` scripts see, not the schedule. `ADMIN_PASSWORD` turns on the dashboard. The paper itself has no auth; it is open to anyone who reaches the domain. The server binds `HOST` (default loopback; the image sets `0.0.0.0`) and answers `GET /healthz` for the compose `healthcheck` (Coolify ignores its UI health page for compose apps and Traefik only routes to healthy containers; the check runs with `node -e fetch(...)` because the image has no curl). Tasks are baked into the image, so prompt changes deploy by push. README has the steps.

### Task layout

```
tasks/<name>/task.json   # config, see below
tasks/<name>/prompt.md   # sent verbatim on stdin to claude
runs/<name>/<runId>/     # gitignored; one directory per run
```

`task.json` fields read by the runner: `model`, `allowedTools` (joined into `--allowedTools`), `timeoutMinutes` (default 15, SIGTERM on expiry), `before` (shell command run in the run dir with `TASK_DIR` set to the task's directory), `contextLabel` (the aside's handle, also used when `output.md` is rendered). `schedule` is a five-field cron string read by the scheduler, in the task's `timezone` (IANA name, e.g. `Europe/London`; both tasks set it so the schedule does not depend on the container's `TZ`). Read by the server: `label` (the tab's text), `lang` (the page's `html lang`), `contextLabel`, `briefsLabel` (the briefs band's heading, "In brief" or "Kısaca"). Extra keys are allowed and are how `before` scripts get their own config (e.g. `tech` keeps its handle list under `"x"`).

Prompts describe the paper in terms of the schema's fields (`title`, sections with `heading`, `lead`, `stories`; stories with `headline`, `body`, `context`, `source`, `importance`) and end by asking for the structured output only. Both prompts tell the model to make a brief (importance 1) of anything worth a line but not a paragraph rather than drop it; `tech` is told the page replaces the newsletters, so it covers every item of every issue that way instead of picking a handful. The schema's field descriptions in `paper.ts` are part of what the model reads, so keep them and the prompts consistent.

### Why the claude invocation looks the way it does

- `ANTHROPIC_API_KEY` is deleted from the child env on purpose so `claude` falls back to the subscription login instead of billing an API key.
- `--strict-mcp-config` stops the headless run from inheriting the user's global MCP servers; a task only gets the tools its own config names.
- Model choice per task: use `haiku` when a `before` script has already fetched all the input and the job is summarizing (`tech`), `sonnet` when the task has to search the web or needs judgement over sources (`haberler` reads pre-fetched X posts but has to filter clickbait and propaganda and reconcile outlets, and its output is Turkish).

### `before` scripts

`tech` chains three: `fetch-x.ts && fetch-hn.ts && fetch-newsletters.ts` (each as `node ../../../scripts/<file>`). They run with the run directory as cwd, and a non-zero exit marks the run `failed` without starting claude; their output is in `before.log`.

- `scripts/fetch-x.ts` writes `tweets.md` (accounts from remote lists), `tweets-web.md` (hand-picked accounts) and `discourse.md` (techtwitter.com's public API, which needs a browser user agent). Posts come from FxTwitter's `/2/profile/{handle}/statuses`, no API key, 6 fetches in parallel. Handles come from two places under `task.json`'s `"x"` key: `lists` (JSON exports in the awesome-ai-x-accounts format, filtered by category id; an entry has a `file` relative to the task directory or a `url`) and `handles` (an object of group name to hand-picked handles). Output is grouped by category. The base AI list is the committed `tasks/tech/accounts.json`; the awesome-ai-x-accounts URL is still listed after it and only adds accounts when it answers, because that repo disappeared once (2026-09-20) and the 50 accounts in the file are what could be recovered from past runs' `tweets.md`. Every run also writes the merged list to `accounts.json` in the run directory, so the base list can be rebuilt from any run.
- `scripts/fetch-hn.ts` writes `hn.md`: the Hacker News front page plus stories over `hn.minPoints` in the last 24h, via the Algolia HN API.
- `scripts/fetch-newsletters.ts` writes `newsletters.md`: new issues from the RSS feeds under `newsletters.feeds` (the four Cooperpress letters and The Deep View's beehiiv feed), converted to text with links kept. It also writes `newsletters.json` (the issue URLs delivered) and scans sibling run directories for earlier `newsletters.json` files, so an issue is delivered exactly once and missed days are caught up. This is the only per-run state that later runs read.

The prompt tells claude to `Read` all five files.

`haberler` (the Turkish daily paper) chains two: `fetch-x.ts && fetch-bundle.ts`.

- `scripts/fetch-x.ts` again, configured under haberler's own `"x"` key with hand-picked handles only (no `lists`, `techtwitter: false`): the most followed Turkish news accounts on X (Pusholder, BPT, Boşuna Tıklama, which aggregate without reporters of their own, and the party-aligned Ajans Muhbir), international Turkish services, independent, left, opposition mainstream, journalists, fact-checkers, economy, sport, and government-aligned outlets (used for facts only, the prompt says so). It replaced the news-site RSS feeds. With `files: 4` and `out: "x"` the posts go to `x-1.md` … `x-4.md`, handles dealt round-robin so each file mixes the groups; `trim: "busiest"` makes the account with the most posts in a file lose its least-liked post first when the file goes over `maxChars`, so the high-volume aggregators cannot crowd out everyone else; `images: true` writes each post's first photo or video thumbnail to `images.json` keyed by the post URL, which is what stories use as `source`. Turkish text and URLs tokenize heavily, so files are kept at 38KB, not 60: at 45KB `Read` still cut off around line 130 and claude had to re-read with an offset. ZAM Haber is left out (suspended); an account that has gone is listed as `failed` in `before.log`. x.com links cannot be opened with `WebFetch`, so the prompt only fetches article links that appear in a post.
- `scripts/fetch-bundle.ts` writes `bundle.md`: the popular list and the last `bundle.hours` of the main feed from Bundle (bundle.app, the Turkish news aggregator app). Bundle has no official API; these are the keyless JSON routes its web client calls on `www.bundle.app/api/main` (`get-popular`, `get-feed` paginated with `beforeRssDataId`, and an unused `get-summary` POST that returns an AI summary with an importance flag), so they can change or block. The prompt uses the popular list as a second cross-source significance signal. It merges each item's `imageLink` into `images.json`.

**Every input file must stay under about 60KB (38KB for Turkish text).** Claude Code's `Read` returns at most about 25k tokens and cuts the rest off silently, which is why tweets are split into two files, post text is cut at 600 chars, the tweet files drop the least-liked posts past `x.maxChars`, and the newsletter file defers older issues past `newsletters.maxChars` to the next run. Check `log.jsonl` read sizes against file sizes when adding a source. techtwitter.com is AI and startup heavy and has almost no web dev content, which is why HN and the web dev handle group exist.
