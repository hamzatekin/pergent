# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

pergent is a personal agent runner. Each task is a prompt plus a small JSON config; running a task spawns headless `claude -p` and stores the result, a structured "paper", on disk and in a SQLite index. The server renders the paper as a plain HTML page, installable as a PWA, that is the morning paper. Prompts and configs are edited in git only. No build step for the Node side; the only build is the stylesheet.

Keep it minimal: one feature per step, verified with a real run.

## Commands

Requires Node >= 24 (TypeScript runs directly via type stripping, so `.ts` files are executed with plain `node` and imports use `.ts` extensions).

```sh
npm run task -- list            # list tasks in tasks/
npm run task -- run <name>      # run one task, print output.md and a status line; exit 1 on failure
npm run task -- costs [name]    # last 20 runs per task from the database: status, turns, minutes, cost, and the average
npm run serve                   # site + API (+ /admin when ADMIN_PASSWORD is set) on http://localhost:4321 (serves dist/ for the stylesheet and static files, so build first)
npm run dev                     # the same with the server restarting on src/ changes and Tailwind rebuilding the stylesheet on save
npm run build                   # Tailwind CLI -> dist/styles.css, plus web/public/ and web/app.js copied into dist/
npm run typecheck               # tsc for src/ (web/app.js is plain JS)
```

There are no tests and no linter. `npm run typecheck` is the only check. The `task` and `serve` scripts (and the Dockerfile `CMD`) pass `--disable-warning=ExperimentalWarning` because `node:sqlite` still prints one on every start.

## Architecture

Nine layers, all small:

- `src/runner.ts` is the core. It loads a task from `tasks/<name>/`, creates `runs/<name>/<ISO timestamp>/`, optionally runs the task's `before` shell command in that directory, then spawns `claude -p --output-format stream-json --verbose --strict-mcp-config --json-schema <PAPER_SCHEMA> --tools <allowedTools> --system-prompt <short>` with the run directory as cwd. On stdin go the task's `inputs` (files the `before` scripts wrote, each in a `<file name="…">` tag; tags rather than headings because the files have headings of their own), then `prompt.md`. It parses the stream for the final `result` event, whose `structured_output` is the paper, and writes `meta.json`, `output.json` (the paper), `output.md` (the paper rendered as markdown, so a run stays readable with `cat`), `log.jsonl`, `stderr.log`, and saves the run to the database at start, after a failed `before`, and at the end. Every child (the `before` shell and `claude`) is spawned detached as its own process group and stopped as a group, SIGTERM then SIGKILL 30s later: killing only the child let a process it started keep the output pipe open, and the run waited on it forever. `before` gets 5 minutes, `claude` the task's `timeoutMinutes`. When the runner itself gets SIGINT, SIGTERM or SIGHUP (a closed CLI terminal, a stopping container) it SIGKILLs the live groups before exiting. Each line of `log.jsonl` gets `t`, the seconds since `claude` started, which the dashboard shows per step. A result without a valid paper (the model answered in text, or the `StructuredOutput` tool call never came) is a failed run.
- `src/paper.ts` is the paper: the `Paper` type (`title`, `sections` with `heading`, optional `lead` markdown and `stories`; a story is `headline`, `body` markdown, optional `context` markdown, `source` URL and `importance` 1-3: 3 leads a section, 2 is a card, 1 is a brief), `PAPER_SCHEMA` (the JSON schema handed to claude, with the field descriptions the model sees), `parsePaper` (shape check on the structured output), `renderPaper` (paper to HTML, the one renderer: headline and headings escaped as text, bodies, leads and asides through `marked`, the source as a "host ↗" chip, the lead image looked up in the run's `images` by the story's source URL with tracking parameters stripped, the aside as a closed `details` whose handle is the task's `contextLabel`; the source chip in `p.foot`, then, when the story has one, Jev's rating as a `.rating` block: the overall score large, next to its three parts as named ten-cell bars with their numbers (Sourcing, Neutral tone, Substance; each coloured by its own level, green from 7, amber from 4.5, red below; what each measures in its `title` tooltip); a section's cards in a `.stories` grid with a lead story two columns wide, then its briefs in one `.briefs` band headed by the task's `briefsLabel`; a run from before `importance` existed gets its first story per section as the lead), `toMarkdown` (paper to the markdown the prompts used to ask for) and `fromMarkdown` (the reverse, for runs from before structured output: `# ` masthead, `## ` sections, `### ` stories, a blockquote opening with a bold label as the aside, a bare URL paragraph as the source). Every run, old or new, becomes a `Paper` before it is rendered, so there is exactly one HTML path.
- `src/rate.ts` rates every story of a finished paper with Jev, TypeSafe's System One model (`POST https://api.typesafe.ai/v1/systemone`, model `jev-latest`, typed questions in, calibrated answers out; docs at docs.typesafe.ai, index at `/llms.txt`). The runner calls it after parsing the paper, only when `TYPESAFE_API_KEY` is set and the task does not set `"rate": false`. One request per story, 8 at a time, retried twice on 429/529. The state is the story as written plus `source_material`: the block of the run's input files that carries the story's source URL (matched with and without its query string), with the nearest `## ` group and `### @handle` headings above it, so the rater sees the original post and which kind of account posted it, not only claude's summary. Three Score questions (`sourcing`, `neutrality` of the original, `substance` of the story), each mapped to 0-10 and combined in code (weights 0.45/0.25/0.3), since Jev is calibrated on judgments, not arithmetic. The result is `story.rating` (`score` and `parts`), added to the paper before it is written, so it lands in `output.json` and the database; it is not in `PAPER_SCHEMA`, the model never sees it. A failed request leaves that story unrated and never fails the run; `rate.log` in the run directory has every score, error and the token count. Jev's primary language is English, so `news`'s ratings are less reliable.
- `src/images.ts` fills in lead images after the paper is written: for every story whose source is an article (not x.com, twitter.com or news.ycombinator.com) and has no image yet, it fetches the page's `<head>` (8s timeout, 512KB at most, 8 at a time, up to 80 stories) and takes its `og:image` or `twitter:image`, https only because of the page's CSP. Found images are merged into `images.json`, which the before scripts start with post photos and Bundle images; `images.log` has the count. Plain HTTP, no model, so it costs nothing in tokens; a failed page is skipped.
- `src/db.ts` is the index over runs: one `runs` table in `runs/pergent.db` (`node:sqlite`, built into Node, WAL mode; the file sits on the `runs` volume) holding the `RunMeta` fields plus `output` (markdown), the `images` map and `paper` (the structured output as JSON, null for runs from before it; added with a guarded `ALTER TABLE` on start). The run directory stays the archive for the log, stderr, `before.log` and the fetched inputs, and is still what you open to debug. `openDb()` creates the table and backfills any run directory with a `meta.json` that has no row yet, so a fresh database (or a restored volume) catches up on start. Deleting a run directory does not delete its row. The `RunMeta` type is the contract; `toMeta`/`saveRun` map it to columns.
- `src/server.ts` is a Hono app on `@hono/node-server`. The reading routes (`/`, `/read`, `/read/:task[/:runId]`) are rendered whole on the server: the chrome (task tabs, older/newer links, the date stamp in the task's `timezone`, the paused-scheduler and failed-run notes) and the paper from `renderPaper`, with the paper's title as the `<title>`. A reader, a crawler and an LLM fetcher get the same page; there is no client-side rendering. `/` and `/read` show the first task's latest ok run; an unknown task or run is a 404. Rendering a page does not count as a read for the scheduler; `web/app.js` sends `POST /api/read` once a page with a run is open, which is what counts (a crawler runs no script, so it cannot keep a forgotten deployment alive). The JSON API stays for curl and debugging, read-only: `GET /api/tasks` (names), `GET /api/tasks/:name/runs[/:runId]` (a run is `meta`, `output`, `images` and `paper`; fetching one also counts as a read), `GET /api/status` (scheduler `off`/`on`/`paused`, last read, pause threshold). Runs start from the scheduler, the dashboard (`src/admin.ts`) or the CLI. Everything else is `serveStatic` over `dist/` (routing is non-strict, so a trailing slash is the same page). The stylesheet and `app.js` are linked with `?v=<mtime>` because the service worker caches by URL and the files are not hashed. Every response carries a CSP (`default-src 'self'`, images from any https host) because the page carries the model's markdown as HTML unsanitized. `onError` passes an `HTTPException` through with its own status instead of turning it into a 500. Binds to 127.0.0.1 only.
- `src/admin.ts` is the dashboard under `/admin`, server-rendered like the paper and styled by the `.admin` rules in `web/styles.css`. It exists only when `ADMIN_PASSWORD` is set (otherwise 404). Login is a form that sets an `HttpOnly`, `SameSite=Strict` cookie holding an HMAC of the password (30 days, path `/admin`; changing the password logs everyone out); a wrong password waits a second, and a POST whose `Origin` parses to another host is refused (our own forms send `Origin: null` because of `no-referrer`). `/admin` has a card per task (last run, average cost of the last 10, 30-day total, a Run now button that calls the server's `startRun`, so it cannot overlap a scheduled run of the same task) and the latest 100 runs with status, turns, time and cost. `/admin/runs/:task/:runId` shows cost by model and tokens from the `result` event's `modelUsage`, `before.log`, `stderr.log` and the steps of `log.jsonl` (text, tool calls with their input, results, all cut short), and links every file in the run directory as plain text (`/files/:file`, only names that `readdir` returns). Pages refresh every 10s while a run is going (a meta refresh, since the CSP allows no inline script). The server marks every row still `running` as `failed` when it starts (`closeStaleRuns`: a deploy or restart replaces the container, so nothing from before can still be going). A row still `running` that is not the task's live run in this server (a CLI run) shows as `stopped`, and only the live run's time counts up. A manual run started after a task's slot counts for that slot, since the scheduler only looks at the latest run's start.
- `src/scheduler.ts` runs tasks on their `schedule` cron string, only when `SCHEDULER=1` (the Dockerfile sets it; a local `npm run serve` never starts runs on its own, use the CLI). It ticks just after every minute boundary and matches five-field cron (`*`, lists, ranges, steps, Vixie-style dom/dow OR) against wall-clock time in the task's `timezone` (an IANA name; without one, the process `TZ`). A task is due when its cron fired in the last 24h and its latest run, whatever its status, started before that slot, so the same rule fires it on time and catches up a slot missed while the server was down, deploying or paused, without ever repeating a run. To trigger a run by hand, use Run now on `/admin`, or run the CLI inside the container: `docker exec -it <container> node --disable-warning=ExperimentalWarning src/cli.ts run <task>` (Coolify's terminal button gets you there too); the CLI does not see the server's in-flight runs, so not while a scheduled run is going. **Dead man's switch:** every run the UI fetches is recorded as `last_read` in the `state` table; after `SCHEDULER_PAUSE_DAYS` (default 7) without one the scheduler stops starting tasks, and the next read resumes it. A fresh database has no read, so a new deployment is quiet until the paper is opened once. This exists so a forgotten deployment cannot keep spending subscription usage; the server checks the pause state while rendering, before `app.js` marks the read, so the page shows a note when runs were paused.
- `web/` is what the browser gets besides the page: `styles.css` (Tailwind v4, built by the Tailwind CLI into `dist/styles.css`; it scans `src/` for the classes `paper.ts` and `server.ts` emit), `app.js` (plain script, no build: ←/→ follow the older/newer links, feed thumbnails narrower than 300px and broken images are removed on load, a portrait or square one is marked `tall` and shown whole (`object-contain` up to 26rem on the inset colour) instead of cropped to the 16:9 frame, which cut vertical video thumbnails in half, `POST /api/read` marks the read, and the service worker is registered except on localhost) and `public/` (manifest, icons, `sw.js`; all copied into `dist/`). No framework, no client-side routing, no web fonts; light paper palette only, system serif. One reading column on a phone; from `md` the page widens and each section's cards (`.stories`) sit in a dense two-column grid, three at `xl`, a lead story spanning two; the section's briefs (`.briefs`) follow as one band whose lines flow in text columns. The PWA `start_url` is `/read`. `sw.js` is network-first for navigations with the last cached front page as the offline fallback, and cache-first for the static files; bump its `CACHE` name when changing what it precaches.

`src/cli.ts` is a thin wrapper over the same runner used by the server.

### Deployment

Coolify deploys `compose.yaml` (one `app` service, port 4321 exposed, `runs` and `claude-home` named volumes, capped at 2 CPUs, 2 GB and 512 processes) from the `Dockerfile` (multi-stage: the Tailwind build, then a slim node 24 image with `@anthropic-ai/claude-code` installed globally, `npm ci --omit=dev` for hono and marked, and `src/`, `scripts/`, `tasks/`, `dist/` copied; runs as root so the volumes are always writable). Coolify's proxy does HTTPS. Variables, set in Coolify's UI: `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`; a container has no browser login). `TYPESAFE_API_KEY` turns on the story ratings. `TZ` is optional: compose defaults it to Europe/London, and it only sets the clock the prompts and `before` scripts see, not the schedule. `ADMIN_PASSWORD` turns on the dashboard. The paper itself has no auth; it is open to anyone who reaches the domain. The server binds `HOST` (default loopback; the image sets `0.0.0.0`) and answers `GET /healthz` for the compose `healthcheck` (Coolify ignores its UI health page for compose apps and Traefik only routes to healthy containers; the check runs with `node -e fetch(...)` because the image has no curl). Tasks are baked into the image, so prompt changes deploy by push. README has the steps.

### Task layout

```
tasks/<name>/task.json   # config, see below
tasks/<name>/prompt.md   # sent verbatim on stdin to claude
runs/<name>/<runId>/     # gitignored; one directory per run
```

`task.json` fields read by the runner: `model`, `allowedTools` (joined into both `--tools`, which limits the built-in tools the model has to exactly these, and `--allowedTools`, which pre-approves them; an empty list is `--tools ""`, no built-in tools at all), `inputs` (run-directory files joined into the prompt ahead of `prompt.md`), `systemPrompt` (replaces the runner's default one), `timeoutMinutes` (default 15, SIGTERM on expiry), `before` (shell command run in the run dir with `TASK_DIR` set to the task's directory), `contextLabel` (the aside's handle, also used when `output.md` is rendered), `rate` (`false` turns off the Jev rating), `effort` (passed as `--effort`: how much the model reasons before answering, billed as output tokens; `news` sets `low`, since its runs spent over 4 minutes and about half of 43k output tokens after the last fetch on a paper of perhaps 20k), `maxOutputTokens` (sets `CLAUDE_CODE_MAX_OUTPUT_TOKENS` for the run; the whole paper is one `StructuredOutput` reply, and one past claude's default 32k cap is cut off mid-JSON and arrives as `{}`, which fails the schema with "must have required property 'title'"). `schedule` is a five-field cron string read by the scheduler, in the task's `timezone` (IANA name, e.g. `Europe/London`; both tasks set it so the schedule does not depend on the container's `TZ`). Read by the server: `label` (the tab's text), `lang` (the page's `html lang`), `contextLabel`, `briefsLabel` (the briefs band's heading, "In brief" or "Kısaca"). Extra keys are allowed and are how `before` scripts get their own config (e.g. `tech` keeps its handle list under `"x"`).

Prompts describe the paper in terms of the schema's fields (`title`, sections with `heading`, `lead`, `stories`; stories with `headline`, `body`, `context`, `source`, `importance`) and end by asking for the structured output only. Both prompts tell the model to make a brief (importance 1) of anything worth a line but not a paragraph rather than drop it; `tech` is told the page replaces the newsletters, so it covers every item of every issue that way instead of picking a handful. The schema's field descriptions in `paper.ts` are part of what the model reads, so keep them and the prompts consistent.

### Why the claude invocation looks the way it does

- `ANTHROPIC_API_KEY` is deleted from the child env on purpose so `claude` falls back to the subscription login instead of billing an API key.
- The input files are in the prompt instead of being `Read` by the model: reading them cost a whole turn, their contents then rode along on every later turn, and `Read` cuts a file off silently at about 25k tokens. `tech` has no tools and writes the paper in its first turn; `news` has only `WebFetch`. `rate.ts` still finds its excerpts in the files on disk.
- `--system-prompt` replaces Claude Code's built-in system prompt, which is written for a coding agent and was sent on every turn. It and both prompts say in so many words to call `StructuredOutput` with the paper as its arguments, `sections` an array: told only to "return the structured output", haiku wrote the whole paper as a text reply, was made to call the tool and wrote it again, and sonnet once passed `sections` as a JSON string, was rejected and wrote it again. Either way the output tokens, the biggest cost of a run, doubled. It does not stop claude loading a `CLAUDE.md` above its cwd: a local run (run directories sit inside the repo) still gets this file; the Docker image has none. `--bare` would skip it but only authenticates with `ANTHROPIC_API_KEY`, not the subscription token.
- `--strict-mcp-config` stops the headless run from inheriting the user's global MCP servers; a task only gets the tools its own config names.
- `--tools` alongside `--allowedTools`: `--allowedTools` alone only pre-approves, so a run could still reach Bash or Edit wherever settings allowed them (a test run of `news` did). `StructuredOutput` stays available, since `--json-schema` adds it (also with `--tools ""`), and a listed `WebFetch` is loaded directly instead of through ToolSearch.
- Model choice per task: use `haiku` when a `before` script has already fetched all the input and the job is summarizing (`tech`), `sonnet` when the task has to search the web or needs judgement over sources (`news` reads pre-fetched X posts but has to filter clickbait and propaganda and reconcile outlets, and its output is Turkish).

### `before` scripts

`tech` chains four: `previous.ts && fetch-x.ts && fetch-hn.ts && fetch-newsletters.ts` (each as `node ../../../scripts/<file>`). They run with the run directory as cwd, and a non-zero exit marks the run `failed` without starting claude; their output is in `before.log`.

- `scripts/previous.ts` (both tasks, first in the chain) writes `previous.md`: the headline and source of every story in the task's ok runs from the last `previous.days` (default 3), newest first, read from sibling run directories' `output.json` and capped at `previous.maxChars` (default 30000; older papers are dropped first). It is the memory: both prompts tell claude to leave out anything already in it and to run a story again only for a real new development, written about the new part. Runs from before structured output have no `output.json` and are not remembered.

- `scripts/fetch-x.ts` writes `tweets.md` (accounts from remote lists), `tweets-web.md` (hand-picked accounts) and `discourse.md` (techtwitter.com's public API, which needs a browser user agent). Posts come from FxTwitter's `/2/profile/{handle}/statuses`, no API key, 6 fetches in parallel, each page tried three times (3s, then 6s apart): FxTwitter pushes back with 404, not 429, and with both tasks fetching in the same minute big live accounts came back 404 and were missing. Handles come from two places under `task.json`'s `"x"` key: `lists` (JSON exports in the awesome-ai-x-accounts format, filtered by category id; an entry has a `file` relative to the task directory or a `url`) and `handles` (an object of group name to hand-picked handles). Output is grouped by category. With `images: true` (both tasks) each post's first photo or video thumbnail goes to `images.json` keyed by the post URL, from the same response, so a story sourced to a post gets its picture at no extra cost. The base AI list is the committed `tasks/tech/accounts.json`; the awesome-ai-x-accounts URL is still listed after it and only adds accounts when it answers, because that repo disappeared once (2026-09-20) and the 50 accounts in the file are what could be recovered from past runs' `tweets.md`. Every run also writes the merged list to `accounts.json` in the run directory, so the base list can be rebuilt from any run.
- `scripts/fetch-hn.ts` writes `hn.md`: the Hacker News front page plus stories over `hn.minPoints` in the last 24h, via the Algolia HN API.
- `scripts/fetch-newsletters.ts` writes `newsletters.md`: new issues from the RSS feeds under `newsletters.feeds` (the four Cooperpress letters and The Deep View's beehiiv feed), converted to text with links kept. It also writes `newsletters.json` (the issue URLs delivered) and scans sibling run directories for earlier `newsletters.json` files, so an issue is delivered exactly once and missed days are caught up. The issue's own URL is taken out of the text (the bare line under the heading and every "Read on the Web" link to it), and `utm_` parameters are stripped from every link: with the issue URL there, the model sourced newsletter stories to the issue instead of the article. It and `previous.ts` are the only things that read earlier runs.

All six files (the five inputs and `previous.md`) are the task's `inputs`, joined into the prompt.

`news` (the Turkish daily paper; the task was called `haberler` until 2026-09-24, and `src/db.ts` moves its old run directories and rows to the new name on start) chains four: `previous.ts && fetch-x.ts && fetch-bundle.ts && filter-jev.ts`.

- `scripts/fetch-x.ts` again, configured under news's own `"x"` key with hand-picked handles only (no `lists`, `techtwitter: false`): the most followed Turkish news accounts on X (Pusholder, BPT, Boşuna Tıklama, which aggregate without reporters of their own, and the party-aligned Ajans Muhbir), international Turkish services, independent, left, opposition mainstream, journalists, fact-checkers, economy, sport, and government-aligned outlets (used for facts only, the prompt says so). It replaced the news-site RSS feeds. With `files: 4` and `out: "x"` the posts go to `x-1.md` … `x-4.md`, handles dealt round-robin so each file mixes the groups; `trim: "busiest"` makes the account with the most posts in a file lose its least-liked post first when the file goes over `maxChars`, so the high-volume aggregators cannot crowd out everyone else; `images: true` writes each post's first photo or video thumbnail to `images.json` keyed by the post URL, which is what stories use as `source`. Turkish text and URLs tokenize heavily, so files are kept at 38KB, not 60: at 45KB `Read` still cut off around line 130 and claude had to re-read with an offset. ZAM Haber is left out (suspended); an account that has gone is listed as `failed` in `before.log`. x.com links cannot be opened with `WebFetch`, so the prompt only fetches article links that appear in a post. It allows at most 5 fetches, all in one turn: runs used to take the whole 10 minutes, and every fetch as its own turn re-sends the ~70k tokens of Turkish input. It also says never to chase redirects or shortened links (bbc.in, trib.al), and caps the paper at 25 stories, 15 briefs and 6 "Ne olmuştu?" blocks: a longer Turkish paper went past 32k output tokens and was cut off. The task sets `maxOutputTokens: 64000` (Sonnet allows 128k) and `timeoutMinutes: 15` as headroom. The dashboard marks a paper step whose input arrived empty (cut off or unparseable); the real output tokens are in the cost-by-model table, since a stream event's usage is from the start of the message.
- `scripts/filter-jev.ts` removes clickbait, filler (horoscopes, guides, lists, ads) and praise or propaganda from the files under `filter.files`, in place, before the model reads them. Each item (a `- ` line and its indented lines) gets one Jev Choice question (`event`, `opinion`, `clickbait`, `filler`, `praise`), 20 items to a request, 6 requests at a time; an item goes only when its kind is a drop kind with probability at least `filter.threshold` (0.8), since Jev reads Turkish less well than English and reads literally (a critical report quoting a minister's "müjde" is a risk). Everything dropped is in `filter.log` with kind and probability; a failed request keeps its items; without `TYPESAFE_API_KEY` nothing is filtered. It is step one of moving `news` to haiku: filtering cuts what haiku would have to read (its window is 200k tokens and news sent about 150k), and the switch waits until `filter.log` shows the judgement holds.
- `scripts/fetch-bundle.ts` writes `bundle.md`: the popular list and the last `bundle.hours` of the main feed from Bundle (bundle.app, the Turkish news aggregator app). Bundle has no official API; these are the keyless JSON routes its web client calls on `www.bundle.app/api/main` (`get-popular`, `get-feed` paginated with `beforeRssDataId`, and an unused `get-summary` POST that returns an AI summary with an importance flag), so they can change or block. The prompt uses the popular list as a second cross-source significance signal. It merges each item's `imageLink` into `images.json`.

**Input sizes.** The per-file caps below come from when the model `Read` its inputs: `Read` returns at most about 25k tokens and cuts the rest off silently, which is why tweets are split into two files, post text is cut at 600 chars, the tweet files drop the least-liked posts past `x.maxChars`, and the newsletter file defers older issues past `newsletters.maxChars` to the next run. With the inputs now in the prompt that limit is gone and the caps (and the split into `x-1..4.md`, and `trim: "busiest"`) could become one size budget per task; they are unchanged so far. What still bounds them is the model's context window (haiku 200k tokens) and cost per run. techtwitter.com is AI and startup heavy and has almost no web dev content, which is why HN and the web dev handle group exist.
